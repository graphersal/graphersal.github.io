Format Versions and Upgrade

Every file of the format starts with a magic and a version. There are two axes (and the single-file container has its own container version):

  • the store format version, in the store's GRAPH file: this release writes and reads version 3 (graphersal::persist::STORE_FORMAT_VERSION); graphersal store info prints it (backend directory (format version 3), format version 3);
  • the file format version of snapshot manifests and segments, WAL segments and packed snapshots (.gsnap): this release writes version 3 (graphersal::persist::FORMAT_VERSION) and reads versions 1, 2 and 3.

File format version 3 needs no upgrade. The store format version stays 3, so a store written by 0.2.x opens as it is: its version 2 snapshots and WAL segments stay and are read as they are, and everything written from then on (a new WAL segment, new snapshots, backups, .gsnap exports) is of file format version 3. From the first such file on, Graphersal 0.2.x refuses the store, its backups and those packed snapshots as written by a newer version (PersistError::UnsupportedVersion, the row below), never as damage. To hand data back to 0.2.x, export it as GraphSON. Files of version 2 never hold a value with digits below the microsecond, an offsettime or a zone name: 0.2.x could not write them.

Two rules bind every release (format specification, section 15):

  • A version from the future is not damage, and a store holding one is never worked on. A file of a newer version (intact magic and header checksum, a version word above this build's) MUST NOT be taken for damage, and a store, backup or single-file store that holds even one such file MUST NOT be worked on in any way: no write, no lock, no repair, no salvage, no maintenance mode, no upgrade, no checkpoint, no backup into or out of it. It is refused as a whole, so this build can never corrupt what a newer one wrote.
  • Format versions move only with a release that needs them. A patch release (x.y.Z) never changes any format version (store, file or container). A format version changes only with a release whose new features need it; a release that changes no format reads and writes the stores of the release before it as they are, with no upgrade.

The upgrade table

Which older store format versions this build upgrades, and how, is one table in the code (UPGRADES, persist/store/upgrade.rs); this copy, and those in the format specification 15.1 and the store upgrade command, are generated from it and checked by a test. An upgrade is done only as its row says: "version word" rows only rewrite GRAPH and GRAPH.copy and are safe in place; "into a copy only" rows refuse --in-place (StoreFailure::UpgradeNeedsCopy) before anything is written; an unsupported version (or one without a row) is refused with PersistError::OlderFormat, whose help is the migration through a packed snapshot (below). A bump of a format version fails that test until the table has a row for the previous version.

Upgrading a store of an older version

Every build reads every released format. A release keeps the readers of every store and file format version released before it (from 0.1.0 on), and the converter that upgrades such a store needs no older Graphersal: graphersal store upgrade reads the older store with this build. The golden fixtures written by the released 0.1.0 binary (crates/graphersal/tests/data/v0.1.0/: a store with history, marks, an attic entry, schema and catalog; a single-file store; a backup directory; a ZIP backup) are upgraded by every test run.

graphersal store upgrade old_store/ new_store/      # into a NEW store; old_store/ is not changed
graphersal store upgrade old.gstore new.gstore      # the same for a single-file store (any backend: new.gstore, a directory, --single-file)
graphersal store upgrade old_store/ --in-place      # the store itself (back it up first)
graphersal store upgrade old_backup/ new_backup/    # a backup directory: it stays a backup
graphersal store restore old_backup.zip new_store/  # a ZIP backup is upgraded as it is restored

In Rust Store::upgrade(from, to) and Store::upgrade_in_place(dir) (any StoreDir: a path, a .gstore file, a MemDir), in Python graphersal.Store.upgrade(source, target) or graphersal.Store.upgrade(source, in_place=True); each returns what it did (UpgradeReport).

What it does:

  • Everything is carried, exactly: the graph, its schema and catalog (saved queries, compression rules), the whole history (snapshots and WAL: every point in time stays a recovery target), the marks, the lineage, the attic entries (they stay restorable or forkable) and every creation parameter, the store id included: the upgraded store is the SAME store in the new format, so an upgraded backup of it continues to take increments.
  • Only GRAPH and GRAPH.copy are rewritten (the store format version word); every snapshot, WAL segment, the marks file and the attic stay byte for byte. This build reads them as they are (each file names its own file format version), so nothing is decoded and encoded again and the history stays exactly what was written. The first commit after the upgrade goes into a NEW WAL segment of the current file format version: a record of the new version is never appended to a segment of the older one.
  • The older store is verified first (every checksum, as store verify does). A damaged store is refused before anything is written (StoreFailure::DamagedSource); repair it instead: graphersal store repair old_store/ --to new_store/ reads a store of an older released version and writes the repaired store in the current format.
  • Into a copy (the default) the older store is only read; its writer lock is held while it is copied, so a store still open by a writer (an older Graphersal, a server) is refused as in use. The copy is verified before its GRAPH is written: an interrupted upgrade never leaves something that opens as a store in the target, and running the upgrade again into it clears what was left and completes.
  • In place the store is verified, then GRAPH.copy and GRAPH are replaced, each atomically: whatever moment a crash hits, the store is either still the older one (run the upgrade again) or already the upgraded one (a reader takes the intact copy), never lost. No other file changes, so no INTENT is needed. Back the store up before (a file copy of the closed store will do): afterwards the older Graphersal refuses it as newer.
  • A store that already has the current format is left alone in place (already_current); a copy of it is refused with StoreFailure::AlreadyCurrent (use store convert or a backup).

Packed snapshots need no converter. A .gsnap written by 0.1.x (file format version 1) loads as it is (--graph graph.gsnap, TraversalGraph::read_snapshot), and graphersal store create new_store/ --from graph.gsnap makes a current store from it (its version 1 segment files are kept byte for byte). That route carries only the graph state, its schema and its catalog.

Store format version 1 was never released. A store of it (no store id) keeps the migration through a packed snapshot: the build that wrote it exports the current state (graphersal --graph old_store/ -e 'g.export_snapshot("graph.gsnap")'), and this build creates a new store from the file. The full recipe: Command Cheat Sheet.

What counts as a format change, and the compatibility promises for third-party readers and writers, are in the format specification, section 15.

Growing without a new version

New kinds of definitions in the catalog (saved queries, property indexes and compression rules today; procedures and others later), new keys of a definition, and new kinds of snapshot files do not change the format version (format specification, section 16). A build that meets something it does not know:

It findsThen
a definition of an unknown kindkept byte for byte and written back unchanged at every checkpoint, fork, backup and repair
an unknown key of a saved querykept and written back
a critical definition of an unknown kind (one that must stay consistent with the data, such as an index), or a snapshot file of a critical unknown kindthe store opens read-only (Store::read_only_reason, PersistError::ReadOnly): reading, verify, export, fork and backups work; writes need the newer version that wrote it

Stores written before the catalog existed open unchanged: their catalog is empty, the first saved query goes into the WAL and the next checkpoint writes it into the snapshot.
