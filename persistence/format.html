The Graphersal Documentation

Storage Format Specification (store version 4, file version 4)

This page is the normative specification of Graphersal's storage format, store format version 4 with file format version 4 (15): the packed snapshot (.gsnap), the write-ahead log (journal), the Store directory and its files, and the single-file container (.gstore). It is written so that a third party can read (and write) these files without Graphersal's code: a backup tool, a converter, a change-data-capture connector that tails the WAL.

The reference implementation is the persist module of the graphersal crate. Where this text and the implementation disagree, it is a bug in one of them; please report it.

1. Scope, conformance and terms

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be read as described in RFC 2119. Byte layouts, numeric constants, magic values, names and the rules that tell a valid file from a damaged one are normative. Default sizes (chunk, segment, thresholds) are informative unless a file records them; a reader MUST NOT assume a default where the file states the value.

2. Conventions

  • Fixed-width integers are little-endian: u8, u16, u32, u64 unsigned, i64 two's complement.
  • uvar is an unsigned LEB128 varint (7 bits per byte, least significant group first, high bit = more bytes follow). A uvar longer than 10 bytes, or one whose value overflows u64, is invalid. Writers MUST write the shortest encoding.
  • svar is a signed integer as zigzag ((n << 1) ^ (n >> 63)) followed by uvar.
  • string is uvar byte length followed by that many bytes of UTF-8. Invalid UTF-8 is invalid.
  • opt_string is uvar 0 for "none", else uvar (length + 1) followed by the UTF-8 bytes.
  • Time is an i64 of microseconds since the Unix epoch, UTC. Commit times of one lineage are monotonic: a commit's time is max(now, time of the previous commit). Commit, mark and checkpoint times and system-journal times of one instance share one monotonic clock: max(now, the latest time the instance wrote); after a restart the floor is the latest time in the WAL and the journal (the floor itself is not stored). Section 18 gives the rules.
  • UUID values and every graph_id are 16 bytes in RFC 9562 network order (big-endian), so that byte order equals the order of the canonical text.
  • Element ids are strings. "Sorted by id" means the bytewise order of the UTF-8 encoding.
  • Checksums are CRC-32C (Castagnoli, polynomial 0x1EDC6F41, reflected, initial value and final XOR 0xFFFFFFFF), stored as u32. "The CRC of bytes a..b" covers exactly those bytes.
  • Reserved bytes and fields MUST be written as zero. A reader MUST ignore reserved bytes unless a section says otherwise.
  • Bounds. Every length or count read from a file MUST be checked against the bytes that remain before anything is allocated for it; a count that the remaining bytes cannot hold is invalid. An uncompressed chunk, single-record WAL body or slice of a commit in parts (9.3.1) is at most 1 GiB; a commit in parts is not bounded by it. A declared uncompressed size of an LZ4 block above 255 * stored length + 64 is invalid.

  • The order of object entries (and of property maps, 7.3) is the insertion order and MUST be preserved. A repeated key in one object or property map is invalid.

  • Temporal values use the proleptic Gregorian calendar. Tags 9 to 13 (file format version 2) have a resolution of one microsecond; tags 15 to 20 (version 3) one nanosecond. A writer of version 3 or later writes ONE form per kind: a date as tag 9, a localdatetime as tag 15, a datetime as tag 16 (tag 17 when it keeps a zone name), a time as tag 18, an offsettime as tag 19, a duration as tag 20; every engine value has an encoding, so nothing is refused. A reader of version 3 or later reads tags 9 to 13 as well (a version 2 segment's chunks copied into a newer snapshot keep them). The svar seconds + uvar nanos pairs hold nanoseconds over the years -9999 to 9999 (about ±3.2 * 10^20 ns, more than an i64) and a duration's whole time part. Their ranges are normative; a value outside its range is invalid:

The zone name of tag 17 is stored as text, never as an index into a build's own table; the offset is stored as written and is not recomputed from the name. A name the reader's time zone database does not know (a newer database's) is content of a newer writer behind a valid checksum: unsupported content (16 rule 9), never damage; the reference reader refuses the value and the operation, as it does with every unsupported content; ASCII case is ignored when the name is looked up. An offsettime orders by its UTC time of day (the local time minus the offset, not wrapped). A duration is not normalized: P1M, P30D and PT720H are three different values.

  • Vector values (tag 14): dimension is 1 to 65536; a component of an f32 or f16 vector is finite (no NaN, no infinity; -0.0 is valid and equals 0.0); the i8 scale is finite and >= 0 (-0.0 is written as 0.0); the value of an i8 component is code * scale; a bit component is 1.0 for a set bit and -1.0 otherwise, and the padding bits of the last byte are 0. An unknown element byte, a dimension out of range and any other violation are invalid (damage): every element kind of version 2 is defined here. A reader checks the payload length (dimension times the component size) against the remaining bytes before it allocates.

  • Blob references (tag 21): a hash_algo of 0, a hash_len outside 1..=64 and a SHA-256 hash that is not 32 bytes are invalid (damage). An algorithm 2..255 is a newer writer's: the value is decoded and kept, and its blob is carried BY NAME (4.6) by every copy (backups, ZIP archives, forks, repairs, packed snapshots), checked by its length and CRC-32C; it is never read and its hash never computed (unsupported content, 16 rule 9). In this version a blobref appears only in catalog definition payloads (6.3); a writer MUST NOT store one as an element property value.

  • Tags 9 to 14 are invalid in a file of format version 1, tags 15 to 20 in a file of format version 1 or 2, tag 21 in a file of a format version before 4 (15): a reader MUST report such a value as damage, never decode it. A reader takes the version from the header of the file the value is in: a segment chunk from its segment's header (7.1, also when the chunk is read through the chunk index without framing the whole segment), a WAL record from its WAL segment's header (9.1), a definition from the manifest (6.1) or WAL segment it is stored in.

  • Readers MUST bound the nesting depth of arrays and objects (the reference reader defaults to 128 levels and is configurable); writers MUST NOT write more than 4096 levels.

A property map is uvar count followed by count pairs of key and value, with keys encoded as object keys are in the same context.

LOCK and BACKUP exist only for directories on a file system; other backends provide the same locks without files (4.3). A snapshot directory holds exactly the files its manifest lists. A directory under snapshots/ named by a commit but without a manifest file is a holder: it is no snapshot (it is not listed, loaded or counted) and only keeps segment files that newer snapshots reference (6.2); a prune removes it when no snapshot uses them any more (12.4).

4.2 Names

Every name a store file records (segment paths in a manifest, paths in INTENT, names in ATTIC) is relative to the store root, /-separated, and contains no empty, . or .. part, no \, no : and no NUL. No store file holds an absolute path, an operating-system path, a device, or the target of a symbolic link. A store is therefore relocatable: moved or copied as a whole, it opens unchanged. A reader MUST refuse a recorded name that breaks these rules.

4.3 Backends

The format does not depend on where the named files live. The reference implementation provides three backends behind one directory abstraction:

  • a directory on a file system (names map to files below the root; parts of the tree MAY be symbolic links to other file systems, which are never resolved or recorded);
  • a single container file (14);
  • memory (no durability; locks are in-process flags).

A backend MUST provide: reading a file or a byte range of it; appending to a file (an append MAY tear on a crash); replacing a whole file atomically (GRAPH, GRAPH.copy, marks rewrites, INTENT, ATTIC); an atomic rename; removal of a file or a directory tree; a durability barrier (fsync of a file and of a directory); an exclusive writer lock; and a shared/exclusive backup pin. Files are only ever appended to, cut back, or replaced whole; lengths are logical bytes.

On a file system, a move between two parts of the tree that live on different file systems is done as: copy into tmp-xdev-<name> in the target directory, sync, rename there, sync the directory, remove the source, sync its directory. Leftover tmp-xdev-* names MUST be ignored by every listing.

4.4 The workload statistics sidecar

WORKLOAD holds the instance's workload statistics (book page "Workload Statistics"): data of the running instance, not of the graph. It is never in the WAL, never in a snapshot, and never copied by a backup, a ZIP backup, a fork, a repair or a conversion; a restored or copied store starts without it. An upgrade into a copy (15.1) keeps it: the copy is the same store. A writable store replaces it whole (write_atomic) periodically and at close.

All integers little-endian. Version 1 has no sections and is still read; in version 2 the sections may be left out (no settings). A section of a tag the reader does not know is skipped by its byte length. The settings of the system jobs (book page "Scheduled Jobs") and the advisor's marks are data of the instance like the statistics: they are lost with the file. A reader MUST treat the file as optional: a missing file, a wrong magic, length or checksum, or a version it does not know means "no statistics" (it starts anew and replaces the file at its next write), never damage, never a reason to refuse the store. A series of a kind or channel it does not know is skipped by its byte length, a tier it does not know by its bucket count; a reader keeps at most 60 minute, 48 hour and 90 day buckets. The magic is none of a segment's or a WAL segment's, so the version guard (15) ignores the file.

4.5 Embedding models

An embedding model the store keeps (book page "Embedding Models in a Store") is ONE blob (4.6) holding all its files as a deterministic tar, referenced by a catalog definition of kind 5 (model, 6.3) that follows the history: every position (commit, mark, snapshot, rollback, view) has exactly the models, and the default model, of that moment. A model enters a store only by an explicit import (one commit defining it) and leaves its current state only by a removal (one commit dropping the definition, refused while the current schema needs the model); its blob goes with the prune that drops the last retained history referencing it (12.4). The identity stays the link between a schema's vector properties (their embedder) and the model: model2vec/<repo>@<12 hex>, the first 12 lowercase hex digits of the SHA-256 of the text model2vec-identity/1\n followed by one line <role> <size> <sha256 hex>\n per identity file, for the roles config, tokenizer and model in that order (the rule of the Model2Vec loader; no path is part of it).

The tar. POSIX ustar (magic "ustar\0", version "00"): one regular-file entry (typeflag '0') per file, entries sorted by name bytewise, mode 0000644, uid/gid 0, uname/gname empty, mtime 0, devmajor/devminor 0, prefix and linkname empty, the checksum as ustar defines it (six octal digits, NUL, space), the size as eleven octal digits and a NUL (so a file is at most 8 GiB - 1), the data padded with zeros to 512 bytes; the end is two zero blocks and nothing after them (a reader accepts further zero bytes only). No directories, links, pax or GNU headers. The same files give the same bytes, so the same blob hash.

Files. The model's own files (the three identity files under the names they had, for example config.json or config_sentence_transformers.json, tokenizer.json, model.safetensors), its card README.md, the repository's licence and notice files (LICENSE*, LICENCE*, COPYING*, NOTICE*), and the manifest graphersal-model.json. Every file name is 1 to 40 bytes of ASCII letters, digits, ., _ and -, not starting with .. A model has at most 64 files besides its manifest. When the repository has no licence file, the writer adds the standard text of an MIT or Apache-2.0 license as LICENSE (license_text template); for every known base-model licence other than license with a bundled text, the file LICENSE-BASE-<licence> (lowercase SPDX id, role license), since parts of a base model (such as a tokenizer) may be in the model.

Manifest (format 3; compact UTF-8 JSON, keys in this order, absent optional keys left out, so the bytes are deterministic; at most 1 MiB):

No time stamp is part of the manifest or the definition (when a model was added is instance data, never part of the immutable model).

Reading. A reader reads the blob whole into memory (after the memory check below) and the tar from it: every header's checksum is checked, sizes are bounded by the remaining bytes, names validated; an unknown type flag, a duplicate or unsorted name, more than 64 files besides the manifest, a manifest that does not list exactly the tar's files are invalid content of the model's blob (never damage of the store, 13). The files are used where they are (no extraction to disk).

Needed models and the open. A model the CURRENT schema needs (a vector property's embedder naming its identity) is loaded when the store opens, in every mode (also read-only, a backup, a view of a past position). A needed model that is not in the catalog of that position, whose blob is missing or damaged, or whose files do not load refuses the open (model_unavailable), with the commands that bring it back; one whose load would take the process over its memory ceiling refuses it too (model_does_not_fit): the check uses the blob's length plus the definition's load_bytes before anything is read, and the message names the smallest ceiling that fits. A writable open records the refusal in the journal (model.load_failed, 4.7) best effort. A model of a family or blob algorithm the reader does not know opens the store read-only (16 rule 9); a reader that cannot run models at all (no Model2Vec loader, such as the browser) checks the needed blobs by length and CRC-32C and opens the store read-only without text queries. A model nothing needs is loaded at the first query that embeds with it; a missing or damaged one is a journal record (model.unavailable), the store works.

Copies. The models travel as blobs: every copy carries the blobs its history references (4.6, 12.x) and the definitions with the catalog, so the copy has the models of every position it holds.

Older stores. Graphersal 0.4.0 kept models as models/<model2vec-12hex>/ directories with a manifest graphersal-embed-model.json (format 2, with added_at), outside the history, carried by every copy as files and by a packed snapshot as segment-table rows of kind 3. A store of store format version 4 has no models/: the upgrade (15.1) migrates each such model into a blob (the tar above, its manifest rebuilt from the old one) and one commit defines them all. A packed snapshot with kind-3 rows imported into a store is migrated the same way (the new store's first commit after the snapshot defines the models; into an open store each is imported).

4.6 Blobs

A blob is an immutable file of the store, named by the hash of its content and referenced from values by a blobref (3, tag 21): hash_algo, the hash, the content's length and its CRC-32C. The hash is the blob's identity (computed when the content is written or arrives from outside, and by a verification); the CRC-32C checks every read; the length is checked, and used for memory decisions, before reading.

blobs/
    3f/3fa1...e9                  a SHA-256 blob: blobs/<first 2 hex digits>/<64 hex digits>
    algo-<n>/3f/3fa1...           a blob of another algorithm n (2..255): its own directory
    tmp-<32 hex digits>           a blob being written (never listed, removed on open)
  • Names are lowercase hex; a blob file holds exactly the content, uncompressed. Anything else under blobs/ is invalid (a verification lists it).
  • Writing. The content is streamed into blobs/tmp-<random> while its SHA-256, CRC-32C and length are computed (constant memory), the file is synced; when a blob of that hash exists and its length and CRC-32C are intact the new file is dropped (deduplication), otherwise (none, or a damaged one) the file is renamed to its name and both directories are synced. The commit that references the blob comes AFTER. Several writers may write the same blob at once.
  • Reading. A missing file, a length other than the reference's and a CRC-32C mismatch are failures of that blob only. A reader checks the length before it allocates.
  • Referenced set. A blob is kept exactly as long as some retained history references it (12.4): the blob tables of the snapshots (6.2 item 5), the ledger (10.1) and the attic entries' WAL. A blob no retained history references is removed by a prune, an attic removal or a rollback delete (12.4, 12.5); a blob written and not yet referenced by a durable commit is kept by the writer that wrote it until its commit.
  • Damage. A missing or damaged blob is NOT damage of the store (13): the damage policy does not apply, the store keeps working, and only what needs the blob's bytes fails. Any copy of a blob with the same hash is the same bytes.
  • The version walk (15) does not read blobs/ (a blob may hold any bytes) nor ledger.

4.7 The system journal

The system journal (book page "System Journal") holds operational events of the instances that wrote the store: opens and closes, checkpoints, backups, prunes, damage, rollbacks, permission denials. Nothing reads it to decide anything: a missing, cut or damaged journal changes nothing of the store, is never damage (13) and never stops an operation; verify lists its problems as notes (12.9).

INSTANCE (instance data: never copied by any copy path, an upgrade into a copy included; regenerated when missing or unreadable):

magic "GRSLINST" | version u32 = 1 | instance id 16 bytes (big-endian) | reserved 28 bytes, zero

The id is a random version-7 UUID, the name the configured instance name, else the host name.

5.3 Two copies

GRAPH is written as two files, GRAPH.copy first and then GRAPH, each through a temporary name (<name>.tmp), fsync and an atomic rename; then the directory is synced. A reader uses: both valid and equal, either; both valid and different, the one with the longer lineage chain, on a tie GRAPH.copy (it was written first, so it is the newer); one valid, that one. A read-write open that found the copies different or one of them invalid rewrites both (and reports it). Both invalid is damage (13).

5.4 The lineage chain

The chain records every lineage the store descends from. A fork's chain is [new id, branched at the target commit, time] followed by the parent's chain; an in-place rollback adds such an entry in the same store; a repair starts a new lineage whose chain continues the damaged store's. An ancestor lineage is valid only up to the branched at of its child entry: a WAL record of an ancestor beyond that commit does not belong to this store's history. A file (a WAL segment, a snapshot manifest) whose graph_id is not on the chain MUST NOT be replayed.

5.5 The store identity

store_id (offset 100; new in store format version 2) identifies the STORE, where graph_id identifies a lineage of its data. It is a creation parameter: a create writes a new random one (128 bits, like a lineage id), and every writer of GRAPH keeps it. A fork, an attic fork (12.5), a repair (13.4) and a conversion to another backend are new stores with a new store_id (their lineage chain still names the parent); an in-place rollback, an attic restore, a compaction, a restored backup (12.6, 12.8) and an upgrade (15.1) keep it: a restore IS the store, an upgrade is the same store in a new version. Every backup (full, increment, ZIP, from memory) records its source's store_id, and an increment requires it to be equal (12.7).

  • Every segment a manifest lists, a referenced one too, carries the manifest's graph_id in its header (7.1): a snapshot of a new lineage (after an in-place rollback) references no file of an older lineage.
  • A reference is resolved in the directory that holds the snapshot: snapshots/ of the store, or of an attic entry (11.2) for a snapshot moved there; a referenced file not found next to a snapshot of an attic entry is resolved in the store's own snapshots/.
  • The referenced file may lie in a snapshot directory or in a holder (4.1). Reading, verifying and loading an incremental snapshot check the referenced files exactly like its own.
  • A writer MUST NOT reference a file that the store's newest snapshot uses (the donor rule of 12.3): a new snapshot references only twins of the newest snapshot's files, held by the snapshot before it.
  • A packed snapshot (8) is self-contained and has no references: writing one from an incremental snapshot names each segment v-NNNNNN.seg/e-NNNNNN.seg by its position per kind and clears flag bit 0 (the manifest is re-encoded; the segment sections are the files' bytes).

payload    = string table | element*            (element count elements)

A chunk is self-contained: its own string table holds every label and property key it uses (string values stay inline), so any chunk decodes alone. References are indexes into that table; a reference outside it is invalid. A vertex's labels are a set (a repeated label is invalid); its first label is its primary label. In a property map and in object values inside a chunk, keys are table references. An edge with an empty property map and one without properties are the same (count 0).

7.4 Footer

footer = (chunk offset u64 | first id string) per chunk | CRC-32C u32 of the footer bytes before it.

The footer allows a binary search by id without reading every chunk.

7.5 Files of other segment kinds

Large data of a future feature (an index, statistics) lives in files of its own, not in the manifest (16 rule 5): a row of the segment table with another kind than 1 and 2 names such a file. Its path is a plain file name in the snapshot's own directory (4.2), its byte length and CRC-32C are those of the whole file; first id, last id and element count belong to the kind (a reader that does not know it ignores them). The file's content belongs to the kind; no chunk index row names it.

  • Kinds 3..127 are ignorable: a reader that does not know the kind checks the file's length and CRC like any segment (a mismatch is damage), copies it wherever the snapshot is copied file by file (backup, import and export of the packed form, 8) and otherwise ignores it. Such a file holds data derived from the snapshot; a writer that does not know the kind does not carry it into a new snapshot (a checkpoint, fork or repair), and a writer that knows it rebuilds it.
  • Kinds 128..255 are critical: a store whose base snapshot has such a row opens read-only for a reader that does not know the kind (16 rule 3).

Assigned kinds: 3, an embedding model's file (4.5), written only into packed snapshots (8): path is <model id>.<file name> (a plain name, at most 64 bytes), first id the model id, last id the file name, element count 0. A reader that knows the kind puts the file into models/<model id>/<file name> of the store a packed snapshot is imported into (never into the snapshot directory) and checks each model against its manifest (4.5); it treats a kind-3 row of a snapshot directory (one a reader without models imported) as a model file when it exports the snapshot again.

4, a blob (4.6), written only into packed snapshots (8), after the snapshot's own rows: path is the blob's hash as lowercase hex (64 digits for SHA-256: a plain name), first id the algorithm's name (sha256), last id empty, element count 0; the byte length and CRC-32C are the blob's, and the manifest's blob table (6.2 item 5) names it. A reader that knows the kind checks the file's SHA-256, length and CRC-32C against the table (foreign input), puts it into blobs/ of the store a packed snapshot is imported into and does not keep the row in the stored manifest; a reader without a store skips it like every ignorable file.

A packed snapshot (.gsnap) is a whole snapshot in one stream:

A packed snapshot exported from a store carries the store's embedding models (4.5) unless the export leaves them out: each model file is a segment-table row of kind 3 (7.5) after the snapshot's own rows, so a named extra file (section kind 5), each model's manifest after its other files. The manifest of the packed snapshot is re-encoded with those rows (its checksums recomputed); the snapshot's own rows and chunk index are unchanged. Importing the packed snapshot into a store moves the model files into models/ and writes the snapshot's manifest without their rows.

The sections appear in this order: the manifest, schema.json, the vertex segments, the edge segments, the named extra files, each in the manifest's table order; the section count is 2 + the manifest's segment count, and each section's length MUST equal what the manifest records for it (for kind 5: the length of name as a string plus the row's byte length; the file's bytes MUST match the row's length and CRC). A new file type therefore needs no new section kind. The manifest and schema.json sections are at most 256 MiB each. The sections are byte-identical to the files of a store's snapshot directory, so a store imports and exports packed snapshots by copying, and a directory snapshot can be read as the packed stream it is equivalent to. A reader of a non-seekable stream checks each section's CRC as it streams and the trailer at the end; nothing follows the trailer.

Writing without seeking (informative). The manifest precedes the segments, every section starts with its length, and a segment file starts with its chunk count and footer offset (7.1), so a writer must know every segment's length, CRC and chunk index before it writes the first segment byte. A writer that neither seeks nor holds the encoded snapshot can plan first: encode every chunk once and keep only its size, CRC and first and last id; write the header, the manifest and schema.json; then encode each chunk again from the same elements and write it. Chunks are self-contained (7.3), so with a deterministic compressor the second encoding yields the planned bytes; the reference writer checks every chunk's CRC against its plan and fails on a difference (the graph must not change in between). A segment's CRC covers its header, which is known only after the chunks; it is the CRC-32C combination of the header's CRC and the CRC of the rest. A store writes a snapshot directory the same way, each segment file as soon as its plan is complete and the manifest last, holding one chunk at a time.

The sync marker and commit_seq lie outside the possibly compressed payload, so a reader can resynchronise after a damaged record by searching for the next position that holds the sync marker, a valid header CRC and a valid body CRC. The separate header CRC makes a damaged length detectable, so it is never taken for an interrupted write (9.6). A record is never split between segments, and neither is a commit: the parts of a commit in parts (9.3.1) are consecutive records of one segment.

9.3 Commit payload

commit   = commit_seq u64 | time i64 | node_sequence u64 | edge_sequence u64 | codec u8 | body'
body'    = body                                  when codec = 0
         | uncompressed length u32 | stored body  when codec = 1 or 2
body     = principal opt_string | attributes property map | uvar mutation count | mutation*

commit_seq MUST equal the frame's. The auto-id sequences are written with every commit so that an id handed out before a crash, a drop or a rollback is never handed out again after a recovery. A writer writes a commit whose body is at most the part size (64 MiB) as this one record, and a larger one in parts (9.3.1); a reader accepts a single-record body up to 1 GiB (the bound of section 2). A commit with a mutation count of 0 is valid: a sequence-only commit, a unit that changed nothing but raised an auto-id sequence (applying a change set whose mutations were all compacted away); replaying it only raises the sequences (and advances the commit position). The attributes are free metadata of the commit (keys inline). Every string is inline.

Op 10 serves every definition kind, so a new kind needs no new op: a define has no before, a removal no after, a change (replace, move, describe) both; at least one is present, and each present image MUST carry the op's kind and name. A definition the reader cannot decode follows 6.3: an unknown kind is kept opaque (and replayed as such), a payload of a known kind that is not a valid property map is damage, and a valid map is never damage (kept, not served, or kept opaque; 16 rule 9). A writer MUST NOT write an after image that is a critical definition of a kind it does not know (16 rule 3).

Mutations are in execution order. Before images are always present: a reader can reconstruct the state before each commit, and CDC consumers get before and after values. The edges a vertex drop removes appear as DropEdge mutations before the DropVertex. A write to a nested path inside a property is a SetProperty of the top-level key.

A schema (op 9) may declare vector rules: a vector property with an embedder and a from property (book page "Vector Rules"). The vectors a rule computes are ordinary SetProperty and RemoveProperty mutations of the commit that changed their source (or of the commit that added the rule, which fills every element of the label), written as they were computed. A replay, a recovery, a merge checkpoint and every other reader apply them as recorded and MUST NOT embed: replaying a commit never needs the model.

9.3.1 Commit in parts

A commit whose uncompressed body (9.3) is larger than the writer's part size (64 MiB) is written as parts >= 2 consecutive records of type 4 (file format version 4); a commit up to the part size stays one Commit record (type 1), unchanged.

frame        = 9.2 frame, type 4, commit_seq = the commit's (equal in every part)
part payload = part u32 | parts u32 | part_body
part_body    = (part = 0) commit_seq u64 | time i64 | node_sequence u64 | edge_sequence u64
                          | body_length u64 | slice
             | (part > 0) slice
slice        = codec u8 | data                         codec 0: data = the raw bytes
             | codec u8 | uncompressed u32 | stored    codec 1, 2 (as in 9.3)
  • The uncompressed slices of parts 0..parts concatenated are body of 9.3 (principal | attributes | uvar mutation count | mutation*); a mutation may span a part boundary. Each slice is compressed on its own (section 2.1).
  • A writer writes slices of 1..=part size uncompressed bytes (all but the last exactly the part size). A reader accepts any slice of 1 byte to 1 GiB (the bound of section 2) and requires their sum to equal body_length. It never allocates from body_length up front: the body grows per part, checked against what it may use.
  • parts is 2..=1048576 (2^20, 64 TiB at 64 MiB per part) and equal in every part; part runs 0..parts without gaps; commit_seq of part 0 MUST equal the frame's. A commit needing more parts is refused by the writer (PersistError::CommitTooLarge, the unit rolls back).
  • The parts of one commit are consecutive records of ONE segment: no other record lies between them (rotation, 9.7, happens only before part 0).
  • A commit in parts is ONE commit for every reader: its position (where a recovery cuts a torn tail, a rollback splits a segment, a backup compares records) is the start of part 0.

9.4 Mark payload

mark = commit_seq u64 | time i64 | name string.

A mark names the position right after commit commit_seq (recovering to it replays up to and including that commit). Its time comes from the instance clock (section 2, "Time"): never earlier than the last commit, nor than any other time the instance wrote. Mark names are unique along a store's whole history (across lineages); a duplicate MUST be refused when it is set.

9.5 Checkpoint payload

checkpoint = commit_seq u64 | time i64: informational, "a snapshot at commit_seq exists". Readers accept and skip it. Commits newer than commit_seq MAY precede it.

9.6 Torn tail and damage

At the end of the last segment (of a recovery's last journal), the following are a torn tail, the remains of an interrupted write:

  1. fewer than 25 bytes that are a prefix of the sync marker (the first up to four bytes match) or all zero;
  2. a frame with a valid header CRC whose payload runs past the end of the file;
  3. zero bytes only, from a record boundary to the end (space the file system allocated that the interrupted write never filled).

A full frame header with a bad header CRC, a full record with a bad body CRC, and any other bytes at the end are damage, wherever they are, also in the last record. Anything that is not a valid record before the end of a segment that is not the last one is damage. A torn tail is cut off by the next read-write open (12.2), never by a reader; damage is never cut (13).

A commit in parts (9.3.1) at the end of the last segment with fewer than parts complete parts (the last present one possibly torn by the rules above) is a torn tail too; it starts at part 0, where it is cut. Damage, wherever it is: a part other than 0 not preceded by its predecessor, a record of another type or commit_seq between parts, part or parts inconsistent, slices whose sum differs from body_length, and an incomplete commit in parts before the end of a segment that is not the last one. A resynchronisation (salvage, 13) that lands on a part other than 0 skips to the next record that is a part 0 or of type 1, 2 or 3; a commit with a damaged part is one damaged region covering all its parts.

9.7 WAL segments in a store

  • Segments are named by the first commit_seq they may contain. Rotation is lazy: before a record (before part 0 of a commit in parts, never between its parts) is written, if the current segment exceeds the segment size (default 16 MiB) or a checkpoint asked for a new segment, the current file is synced, and a new segment named by the next commit sequence number is created with its header, synced, and its directory synced. A Mark or Checkpoint record may therefore be the first record of a segment named commit_seq + 1 of the commit it refers to. Only the last segment can end in a torn record.
  • The replay set of a snapshot at position S is the last segment whose name is <= S + 1 and every later one. Commit records <= S are skipped; every later commit record MUST be exactly the previous + 1 (else the history has a gap: damage).
  • After an in-place rollback or a fork, the new lineage writes a new segment (its header carries the new graph_id).
  • A record whose write or sync failed is cut off again (the file truncated to the record's start, for a commit in parts to the start of part 0, whatever part failed, and synced) before the writer refuses further commits. When that cut fails, the valid end is recorded in GRAPH (flag bit 1); readers MUST read only up to it, and the next read-write open truncates the segment there and removes later segments.

9.8 The newest segment and a clean close

A cut of the last WAL record is indistinguishable from an interrupted write and is treated as a torn tail. A segment that is missing, emptied or replaced by another segment's bytes must never be: it would silently open the store at an earlier commit. Without a metadata write per commit, GRAPH therefore records:

  • wal_head (flag bit 3, offset 84): the name of the newest WAL segment, written whenever a segment is started, after the segment's header was written and synced and its directory synced (rotation, the first segment of an open, the segment target + 1 of a rollback together with its lineage entry), and after an attic restore (the newest restored segment); a recorded WAL cut lowers it to the cut segment. A failed write leaves the older value.
  • closed_at (flag bit 4, offset 92): the last commit at a clean close (state 0). A catalog commit on a closed store (12.12) moves it forward to that commit; it never lowers it.

At every read-write open (before the torn-tail rules), in the damage scan and in verification it is damage when: a segment's header names another first commit than its file name; the segment wal_head is missing, or it or an older segment is shorter than its 64-byte header; or the store was closed cleanly at closed_at and the snapshot plus the WAL end at an earlier commit. A last segment newer than wal_head and shorter than its header is a crash while it was being started: it is removed as a torn tail.

9.9 Write ordering and durability

The writer of a journal MUST:

  1. assign the commit's sequence number (checked against overflow) before writing its record;
  2. run every other commit check (hooks that may veto) before writing, so that nothing fallible follows a written record and the WAL never holds a commit that did not happen;
  3. write the record (every part of a commit in parts, 9.3.1), then make it durable according to the configured durability: a sync after every commit (the default), at most once per interval, or left to the operating system; a commit in parts gets one sync, after its last part;
  4. treat a failed write or sync as a vetoed commit (the unit rolls back) and refuse every later commit and mark until the WAL is reopened, because the state of the file is unknown.

The durable end is the offset after the last record whose sync completed; it moves only after the last part of a commit in parts, so it never lies inside one. Records after it may still be vetoed and MUST NOT be copied by a backup (12.6).

10. The marks file

A derived list of the store's marks: append-only frames length u32 | CRC-32C u32 of the payload | Mark payload (9.4), appended and synced after the Mark record is durable in the WAL. The WAL is the source of truth: a missing or damaged marks file is rebuilt from all WAL segments on open, and marks in the replayed WAL that the file lacks are appended. Listing marks reads only this file and lists only the marks a target can reach: those at or after the oldest snapshot of the store (or backup) listed. The file is not rewritten by a prune (12.4): a backup copies it and may still reach older marks with older snapshots of its own. A mark that is not listed keeps its name taken; resolving it as a target fails.

10.1 The ledger file

A derived list of blob reference changes (4.6): append-only frames length u32 | CRC-32C u32 of the payload | payload, payload = commit_seq u64 | graph_id 16 bytes (big-endian) | blobref (3, tag 21, without the tag) | delta svar: one frame per (commit, blob) whose net delta is not 0, the delta counting every blobref in the commit's after images (+1) and before images (-1). Frames are appended and synced after the commit is durable in the WAL. The WAL is the source of truth:

  • A frame counts for a position when its graph_id and commit_seq lie on that position's lineage chain (5.4): its lineage is on the chain and its commit at or before that lineage's branch point. A rollback does not rewrite the file: frames of an abandoned lineage are ignored by this rule.
  • A damaged file, and a missing one in a store that holds blobs, is rebuilt from all WAL segments on open (a warning and a journal record ledger.rebuilt, never damage). After a crash the frames of the replayed commits the file lacks are appended and frames of the current lineage after the recovered end are dropped. A store that never referenced a blob needs no ledger.
  • A prune rewrites it (atomically) without the frames at or before the oldest kept snapshot and without the frames off the current chain (their history lives on in attic entries, whose WAL is read for them); no INTENT is needed (the file is derived).

11. The INTENT and ATTIC files

11.1 INTENT

A multi-file operation writes INTENT (compact JSON, replaced atomically and synced) before its first file change and removes it after its last one. Every step is idempotent; a read-write open that finds INTENT completes (or, for a backup increment, rolls back) the operation before anything else. An unknown op MUST fail the open, as unsupported content of a newer writer (16 rule 9), never as damage. Every path in it follows 4.2.

11.2 ATTIC and attic entries

An attic entry is a directory attic/<YYYYMMDDTHHMMSSZ>-<first moved commit, 20 digits>/ with the moved snapshots/ and wal/ and an ATTIC file (the name is unique: when it is taken, by an entry or an entry being removed, the time part is advanced by one second until it is free; the ATTIC file records the exact time): compact JSON with the string values graph_id (the old lineage), new_graph_id, target, last_commit, time, reason, base_snapshot and kept_bytes. An entry being removed is first renamed attic/removing-<id> (removed at the next open).

An entry is self-sufficient given the store (it never needs another entry). Its history is its base snapshot (base_snapshot, a snapshot of the store's own snapshots/), then the store's WAL from it up to the prefix end, then the entry's own WAL; or, when the entry holds snapshots, its newest one and its own WAL after it. The prefix end is the commit before the entry's first WAL segment, at most its target. Segments of the entry named at or before its target are its prefix: copies of the store's history that a later rollback to an earlier commit (rebase, 11.1) gave it before moving that history into its own entry; the same rollback points base_snapshot at its own base and drops the entry's snapshots when they reference files it moves (they are derived: the entry's WAL rebuilds every state they held). The store's history up to an entry's prefix end therefore stays in the store: rollbacks keep everything at or before their target, restores add only history after theirs, and prune keeps every entry's base and the WAL after it (12.4). The entry's segment and snapshot listings treat a missing snapshots/ or wal/ as empty.

12. Operations

12.1 Load and recovery

A target is Latest, a commit_seq, a time (the last commit whose time is at or before it), or a mark name. Loading a target: take the newest snapshot at or before the target (for Latest, the newest), then replay its replay set (9.7) along the lineage chain (5.4) up to the target.

  • A load checks GRAPH and the lineage, may check the manifest's estimated in-memory bytes against a budget, loads the vertex segments, then the edge segments (an edge's endpoints are resolved by id), rebuilds every index and statistic, and restores the graph_id, the position, the last commit time and the auto-id sequences.
  • A snapshot load does not validate the data against the stored schema: the data was valid when it was committed, and integrity comes from the checksums. It restores the catalog of definitions from the manifest (6.3).
  • WAL replay applies mutations without running commit hooks or schema validation; op 10 stores or removes a definition.
  • A read-write open whose loaded state holds a critical definition of a kind the reader does not know, or whose base snapshot has a file of a critical segment kind it does not know (7.5), opens the store read-only (16 rule 3): every commit, mark, checkpoint, prune, rollback and compaction is refused, and nothing is written after the load (no torn-tail cut, no marks rebuild, no change of GRAPH). The steps of 12.2 before the load (completing an INTENT, removing leftovers, applying a recorded WAL cut) MAY have run; they do not change the graph. Reading, verification, export, fork and backups work; a fork or backup keeps the definition and is read-only for that reader too.
  • A read-write open whose snapshot schema.json or a schema image of op 9 the reader cannot parse (a newer writer's keyword or mode; its checksum is valid) loads the data WITHOUT the schema and opens the store read-only in the same way (16 rule 9). As the loaded state lacks the schema, every store operation that would write a state derived from the files (a checkpoint, a fork, a repair) is refused as unsupported; a file-level backup and the export of a stored snapshot copy the bytes as they are. A snapshot written from the loaded graph in memory (g.export_snapshot) has no schema.
  • Recovery to a target before the end yields a read-only past state. A writable state from it is either a fork (a new store, 12.5) or an in-place rollback.
  • Without a snapshot (a journal over a stream), the first journal MUST start at commit 1.

12.2 Open and close

A read-write open: take the writer lock (12.10); complete an INTENT; remove leftovers (snapshots/tmp-*, *.tmp); apply a recorded WAL cut; run the checks of 9.8; load (12.1, mode Latest); cut a torn tail of the last segment; rebuild marks if needed; set GRAPH state 1. A clean close: sync, then write GRAPH with state 0 and closed_at. A store whose state is 1 at open was not closed cleanly; that is not damage (the WAL replay recovers it).

12.3 Checkpoints

A checkpoint writes a snapshot of the current state: encoded consistently at one position (the reference implementation streams it chunk by chunk, see 8, or merges it, below), into snapshots/tmp-<32 hex>/, every file synced, the directory synced, verified (manifest CRCs, schema.json, every segment's length and CRC, every chunk CRC and the chunk index), renamed to its 20-digit name, snapshots/ synced; then a Checkpoint record is appended and a new WAL segment is requested. The manifest carries the whole catalog of definitions, every definition of an unknown kind byte for byte as read (6.3). Only renamed snapshots exist for listing, loading and retention. A checkpoint at a position that already has a snapshot returns that snapshot. The chunk target size is the store's (GRAPH offset 44) for its whole life.

Merge checkpoint. A writer MAY build the new snapshot from the newest snapshot (the base) and the WAL after it instead of from a loaded graph (the reference implementation does, without the graph's lock, unless the WAL after the base exceeds a configured bound). Such a writer:

  • reads the WAL only up to its durable end (9.9), from the base's replay set (9.7) along the lineage chain (5.4), with every header and body CRC, commit continuity and every lineage rule of a load; the new snapshot's position is the last commit read and its graph_id the lineage the replay ends in (an empty segment of a new lineage counts);
  • applies the commits as a load replays them (12.1) to the base's state of every element they name, and MUST check every mutation's before image against that state: a mismatch (the WAL does not continue the base) is damage;
  • reads every base chunk it uses with its CRC and chunk index row, every base segment it rewrites in full (header, chunks, footer, file CRC), and verifies the new snapshot, referenced files included, before the rename;
  • carries the schema, the catalog (unknown non-critical definitions byte for byte), the auto-id sequences, the position and the last commit time exactly as a load followed by a checkpoint would; drops files of an ignorable unknown segment kind (7.5); refuses a base or a state with something critical it does not know (16 rule 3);
  • rewrites every segment that holds an element a commit names (an element whose id falls between two segments' ranges goes to the later one, beyond the last range to the last one); the rewritten elements are in strictly increasing id order across the new segments;
  • keeps every other segment of the base byte for byte under the donor rule: the new snapshot uses no file the base uses, so the base stays an independent copy of every id range, the donor of 13.4. Such a segment is referenced (6.2) when the snapshot before the base (the newest snapshot older than the base, of the same lineage) has a twin: a row with the same kind, first and last id, element count, byte length and file CRC, the same chunk index rows, naming another file than the base's (after resolving both, 6.2); the reference names that file. Otherwise the segment's bytes are copied into a new file of the new snapshot (read with the file CRC checked). So an unchanged range alternates between two files from checkpoint to checkpoint, and only the first checkpoint after the range was rewritten copies it. A writer that encodes a loaded graph (8) writes only new files and meets the rule too;
  • on damage, writes nothing visible: the temporary directory is removed, no file of the store changes.

A closed store MAY be checkpointed the same way by a process that takes the writer lock (12.10), completes an INTENT and removes leftovers (12.2); it ignores a torn tail of the last segment, honours a recorded WAL cut, applies the checks of 9.8, and appends no Checkpoint record.

12.4 Prune and retention

prune(up_to) keeps every snapshot from min(newest snapshot <= up_to, second-newest snapshot) on, plus the base snapshot of every attic entry; it verifies each kept snapshot first, then removes the older snapshots and the WAL segments before the replay set of the oldest kept one, under an INTENT (prune). The last two verified snapshots and the WAL between them always stay (the donors of 13.4). Nothing is ever removed implicitly. Prune is refused while a backup holds the pin (12.10). Marks before the oldest kept snapshot become unreachable (10); a prune reports them, from the marks file only.

Files that a kept snapshot or a snapshot of an attic entry references (6.2) stay: of a removed snapshot directory that holds one, only the other files are removed, the manifest first (the directory is a holder from then on, 4.1); a holder older than the oldest kept snapshot that no such snapshot uses any more is removed whole. The INTENT's files then name single files of such a directory. Under the donor rule (12.3) the last two snapshots share no file, so each is the other's donor. A rollback that deleted the history using a holder's files, and the removal of an attic entry whose snapshots used them, remove the files no snapshot of the store or of an attic entry references any more (and the holder when it is left empty); a file nobody references is never referenced again (a checkpoint references only files of a listed snapshot), so this needs no INTENT.

Blobs (4.6). The referenced set R of a store is the union of the blob tables (6.2 item 5) of every snapshot of the store and of its attic entries, the blobs of the ledger frames (10.1) on the current chain, the blobs every attic entry's own WAL references, and the blobs a running writer holds (written, its commit not yet durable). After its own removals a prune rewrites the ledger (10.1) and removes every blob file not in R (the orphans of interrupted writes too); an attic removal and a rollback delete do the same. A removal is idempotent and needs no INTENT (a blob not in R is never referenced again). When the referenced set cannot be read nothing is removed.

12.5 Fork, in-place rollback, attic

  • Fork: load the target (12.1) and write it as a new store: one snapshot (with the catalog, 6.3), a new graph_id, the manifest's parent fields set, the chain [new id, branched at target, time] + the source's chain. Marks are not copied.
  • In-place rollback (move or delete), under INTENT rollback (11.1): everything after the target (later snapshots, the WAL after it; the segment holding the target is split) moves into an attic entry or is deleted; the store continues as a new lineage in the same root.
  • Attic restore (11.1) undoes a rollback while nothing was committed or marked since; an attic fork writes the entry's history as a new store. Prune never removes an attic entry's base snapshot except together with the entry.
  • Every attic entry stays whole after any sequence of rollbacks, restores, removals and prunes (11.2): a rollback to a commit before an older entry's history copies what that entry needs into it first (11.1 copies, rebase, drop). Entries never depend on each other: removing, restoring or forking one never breaks another. Restore order (normative): an entry MAY be restored only while GRAPH's current graph_id equals the entry's new_graph_id (the lineage its rollback started) and nothing was committed or marked since; after several rollbacks the entries therefore restore newest first, each restore bringing back the lineage the next older one needs. A writer MUST refuse an out-of-order restore without changing any file, and SHOULD name the newer entry to restore first. Any entry MAY be forked at any time.
  • A rollback or restore that fails once its INTENT is written leaves the files ahead of the graph in memory: the writer refuses every further change and its close writes no GRAPH; the next open completes the operation.

12.6 Backups

A backup is a file-level copy that takes no graph lock: snapshots are immutable once renamed and the WAL is append-only. A full backup copies GRAPH (rewritten: state 0, no WAL cut, the backup marker, wal_head and closed_at of the backup's own files) to GRAPH and GRAPH.copy; the marks file as read before the copy ends were fixed (every mark in it is in the copied WAL); the latest snapshot (verified before and after the copy) with the files it references (6.2, copied under their names, in holders when their snapshot is not copied) and its replay set, the segment of the durable end cut at the durable end, later segments left out. A copy by another process, which has no durable end, copies the last segment up to its last complete record (a torn tail, 9.6, is left out; damage before it stops the backup), never past a recorded WAL cut. LOCK, BACKUP and the attic are not copied. During the copy the source's BACKUP pin is held shared.

Blobs (4.6). A full backup copies the blobs its copied history references: the blob table of the copied snapshot (6.2 item 5) and the blobs the commits of the copied WAL reference, each checked by length and CRC-32C in the source and again in the copy (streamed). A blob missing or damaged in the source is not carried (a warning; the backup's catalog still references it): blob damage is never damage of the store. The ledger (10.1) is not copied: it is derived, and a backup's history is read from its WAL.

Verification. A backup (full, increment, ZIP) reads every checksum of what it copies in the SOURCE before it writes anything, and again in the COPY after writing it:

  • in the source: both GRAPH copies (one unusable copy is a warning, both are damage; the backup writes two fresh ones); the marks file (derived, 10: damage is a warning and the backup's is rebuilt from the WAL it copies); every snapshot it copies with everything 12.3 verifies (manifest CRCs, schema.json, every segment and chunk, the chunk index, referenced files) and both copies of the manifest's fixed part (one damaged copy is a warning: the backup gets the file with the intact copy in both places, byte for byte what the writer wrote); every WAL record of every segment it copies, header and body CRC, each segment's header against its name (9.8) and the lineage chain, the segment set of 9.8, and commit continuity (every commit the previous + 1; the first commit after the snapshot, or after the backup's position, its successor);
  • in the copy: GRAPH, GRAPH.copy and marks byte for byte as written, every snapshot as 12.3 verifies it (both fixed copies strictly), every WAL segment read again with the same end and the same commits as the source's; a ZIP archive is read back entry by entry (12.8).

Damage in the source stops the backup before anything is written; damage of the copy removes a new backup and rolls an increment back (for an increment, the backup's old GRAPH is written first, so the rollback never takes a final GRAPH that did not read back for a completed one). When the copy does not read back, the source's checks run again: a source that fails them now is the source's damage. The report lists each problem with its file, offset and reason, as verification does (12.9), and names the side; the remedy for damage in the source is a repair of the SOURCE (13.4, never of the backup), or, while the source is open in a process whose graph is intact, a backup from memory (12.11).

Marker. Flag bit 2 marks a backup; offset 68 holds the last commit it holds and offset 76 when it (its last increment) was taken. graph_id, store_id and the lineage chain are the source's. A marked store never opens read-write; read-only loads, verification, listing, export, fork, prune of the backup and backups of it work. Restoring a backup in place takes the writer lock, rolls back an interrupted increment, clears bit 2 and the marker fields and writes GRAPH clean: the root is then the live store with the same graph_id and store_id.

12.7 Incremental backups

A backup into a root that holds a marked backup is an increment; into an empty or missing root, a full backup; anything else is refused (a store that is not a backup is never written to).

  • Relation. The backup's chain MUST equal the tail of the source's chain that starts at the entry with the backup's graph_id. With that entry at position k > 0, the backup may hold commits only up to the smallest branched at of the entries 0..k-1 (a rollback of a later lineage to before its own start branches from an ancestor at an earlier commit); a backup holding more (the source was rolled back behind the backup's position) is refused; a full backup into a new directory follows the new history, and the old backup stays as the archive of the abandoned one. Unrelated stores are refused.
  • Identity. The backup's store_id (5.5) MUST equal the source's. A fork, repair or conversion of the backed-up store shares its lineage chain up to the copy but is a different store: its increment is refused, and a full backup into a new directory is needed.
  • Position. The backup's position is the larger of its newest snapshot and the last commit of its WAL; its last segment L MUST end with a complete record.
  • WAL. If the source has a segment named L with an equal 64-byte header: the source's copy end MUST be at least L's length, and the 25-byte frame of L's last record MUST equal the source's bytes at that offset (prefix check); the bytes from L's length to the copy end are appended. Equal name, different header: allowed only when L holds no commit record and the source branched from the backup's lineage (a rollback to exactly the backup's position); the source's segment then replaces L. The source has no segment L (pruned): its next segment MUST be named at most position + 1, else the gap is refused and a full backup is needed. Every source segment named after L, up to the durable end, is copied whole.
  • Snapshots. Every source snapshot newer than the backup's newest is copied, verified before and after. A referenced file (6.2) the backup lacks (its snapshot was written and pruned since the last increment) is copied from the source, under its name, before the snapshots that use it, and listed in the INTENT's files; one the source lacks too is refused.
  • Steps, with the backup's writer lock held and the source's pin shared: complete or roll back an earlier interrupted increment; write INTENT backup_increment; when the lineage changed, write GRAPH with the source's chain and the OLD marker; copy each snapshot through snapshots/tmp-<hex>/ (synced, verified, renamed); append the tail and sync, re-reading every record of the segment; copy a replacing segment and each new segment through <name>.wal.tmp (synced, re-read, renamed; a replaced L is first renamed <name>.wal.replaced); check that the copied commits continue the backup's WAL without gap or overlap; write marks; write GRAPH with the source's identity, clean, no WAL cut, the new marker; remove the .replaced file; remove INTENT. The backup is a valid store after every step.
  • Interrupted increment (found at the next backup, restore or prune of the backup): when the marker's time equals the intent's taken_at, the increment is complete (remove .replaced and INTENT); otherwise it is rolled back: the listed files and every snapshots/tmp-* and wal/*.tmp removed, a .replaced segment renamed back, the tail cut to tail_len, GRAPH rewritten from graph_before, marks rebuilt from the WAL, INTENT removed.
  • Nothing pins the source's WAL for a backup: a prune of the source can make the next increment impossible (a full backup is then needed).
  • Blobs (4.6): after the increment, every blob the backup's history references that it lacks is copied from the source (checked by length and CRC-32C on both sides); nothing is removed (a prune of the backup, 12.4, collects).

12.8 ZIP backups

A full backup MAY be written as one ZIP archive: stored entries (method 0), UTF-8 names (the store's names, 4.2), DOS time 1980-01-01 00:00, the CRC-32 (IEEE, as ZIP requires) in the local header, zip64 extended fields always (sizes in the local header, sizes and offset in the central header), then the zip64 end record, its locator and the end record. The archive's GRAPH carries the backup marker; unpacking it is the explicit restore and clears the marker. A reader MUST accept only the store's names and MUST refuse compressed, encrypted or streamed (data descriptor) entries. A well-formed name outside the layout it knows (plain segments, at most four) is a newer writer's file: the restore is refused as unsupported, never as damage (16 rule 9); any other name is damage. The reference writer reads the archive back after writing it (12.6): every entry's CRC-32 and every checksum of the store files in it, which arrive in an order a one-pass reader can check (GRAPH, GRAPH.copy, marks, then each snapshot's manifest before its other files, then the WAL segments, then the blobs, blobs/<2 hex>/<hash> (4.6: each read back with its length, CRC-32C and SHA-256), then the segments of the system journal, journal/<20 digits>.jnl, 4.7: checked frame by frame, a problem is a warning). Unpacking an archive checks every blob as foreign input: the SHA-256 of its content against its name, its length and CRC-32C against every reference its history holds; a mismatch refuses the restore as damage of the archive. A writer MAY leave the models and blobs out of an archive meant to be shared (the reference implementation's BlobCopy::Exclude): its catalog still references them, so the receiver has them missing.

12.9 Verification (scrub)

Verification reads every checksum: both GRAPH copies, every manifest (both fixed copies), every schema.json, every segment and chunk (and the chunk index), every WAL record; it checks id order and non-overlapping ranges, WAL continuity (commit_seq + 1 per Commit, no gaps) along the lineage chain, the checks of 9.8, every attic entry (its history is rebuilt as 11.2 describes, and each of its snapshots verified), and the marks file. A holder (4.1) with files that no snapshot of the store or of an attic entry references is a problem (a lost manifest, or files a prune left). A segment file the newest snapshot shares with the previous one (a break of the donor rule, 12.3) is a warning, not damage: the range has no independent donor; the next checkpoint finds no twin for it and copies it. It is meant to be run regularly: it finds damage while donors still exist. Verification also checks every embedding model (4.5): its manifest, the set of files, every file's size and SHA-256; a model of a newer manifest format is a note. It reads every segment of the system journal (4.7): a damaged record or segment is a note, never a problem. It reads every blob of the referenced set (12.4) whole: SHA-256, CRC-32C and length; a missing or damaged blob, and an entry under blobs/ that is not a blob's name or tmp-*, is a problem with its path under blobs/ (never damage of the store, 13); a blob file outside the referenced set is a note (an orphan the next prune removes); a blob of an unknown algorithm is checked by length and CRC-32C only, with a note that its hash was not checked.

12.10 Locks and pins

  • Writer lock: at most one writer per store. On a directory it is an exclusive operating system advisory lock (flock / LockFileEx) on LOCK, held while the store is open read-write; in a container file it is the lock on the file itself (14.5). Read-only loads, verification, listing, export, fork and out-of-process backups take none.
  • Backup pin: a backup holds the BACKUP lock shared while it copies (waiting while a prune holds it); prune takes it exclusively and without blocking, and is refused while a backup runs.

12.11 Backups from memory

A writer that holds a store open and has found damage in its files (13.3) MAY write a backup of its graph in memory instead of copying files: the graph was verified when it was loaded and changed only by commits since. It reads and writes NOTHING in the store's directory. The backup is an ordinary marked backup (12.6):

  • snapshots/<seq>/: one snapshot of the graph at its last commit seq, written through snapshots/tmp-<hex>/, synced, verified (12.3) and renamed;
  • wal/<seq + 1>.wal: an empty WAL segment of the graph's lineage (its header only), synced;
  • GRAPH and GRAPH.copy: the store's identity, lineage chain and creation parameters (5.2) with state 0, no WAL cut, the backup marker (seq, the time), wal_head seq + 1, closed_at seq; read back. No marks file: like a fork, the backup holds no WAL before its snapshot, so the marks would not be targets.

Into a missing or empty root it is a full backup. Into a marked backup of the same store (the relation of 12.7, and its position at most seq) it is an increment under an INTENT backup_increment whose files are the new snapshot directory and segment: the snapshot is newer than everything the backup holds, the commits between the backup's position and seq are not in it (no target between them). A later file-level increment of such a backup finds no segment of the source it continues and is refused: a full backup is needed.

The blobs the graph's state references (the new snapshot's blob table) are copied from the store's blobs/ leniently: the one exception to "reads nothing in the store's directory", since blobs live only there; one that is missing or damaged is listed as not carried.

12.12 Catalog commits on a closed store

A writer holding the writer lock of a CLOSED store MAY append one commit that changes only the schema (op 9) and the catalog (op 10), computed WITHOUT loading the elements (book page "Embedding Models in a Store"). No byte changes: the record is an ordinary Commit (9.3, a single record: such a commit is small) and the next open replays it like any commit.

  1. The catalog view: the newest snapshot's definitions table (6.3, with the forward-compatibility rules of 16: opaque definitions kept) and schema.json, then every record of the WAL after it in the replay set (12.1) up to the last complete record: a Commit's ops 9 and 10 applied with their before images VERIFIED against the view (a mismatch is damage), its data ops read (frames and checksums checked) and skipped; continuity, lineage (5.4) and 9.8 as for a recovery. The last commit's position, time and id sequences are the new commit's base (the manifest's without WAL commits). Damage refuses the commit with nothing written.
  2. A store this version may only read (a critical opaque definition or segment kind, 16 rule 3; a schema it cannot parse) is refused.
  3. Before appending, the writer MUST do what an open does to the WAL: apply a recorded wal_cut (9.7) and write GRAPH without it, remove an unstarted last segment and cut a torn tail (9.6), complete the marks file (10) and the blob ledger (10.1).
  4. The commit continues the last segment unless it is of an older file format version (never continued, 15) or past the segment size: then a new segment (9.7, wal_head). Its time is at least every time the files hold (commits, marks, checkpoint records, the system journal's tail). It is synced before anything follows; a failed write is cut off again or its cut recorded (9.7). Then its ledger frames.
  5. GRAPH: a store closed cleanly records the new commit as closed_at (it MUST NOT be lowered); a crashed store (state 1) stays as it is. A crash between the commit and this write leaves a WAL ending later than closed_at, which is valid (9.8).

A reader without the lock (--read-only) sees at most an unfinished last record, which it ignores (9.6). No snapshot is written.

13. Damage handling

13.1 Redundancy

  • GRAPH and GRAPH.copy (5.3); the manifest's fixed part at its head and its tail (6).
  • The manifest's chunk index (6.2) carries the id range and CRC of every chunk.
  • WAL frames carry a sync marker and commit_seq outside the payload (9.2).
  • Retention keeps the last two verified snapshots and the WAL between them (12.4), and the donor rule (12.3) makes them independent: the newest snapshot shares no segment file with the previous one, so every id range of the newest has a donor in a distinct file (the previous snapshot's chunks plus the WAL between the two), and every range of the previous one has a later snapshot covering it. A file the newest snapshot references is a twin in the directory (or holder) of an older snapshot; its damage is repaired from the previous snapshot like damage of the newest's own files.
  • Flag bit 0 of GRAPH is reserved for parity data (not in store format version 4).

13.2 The damage scan

Chunks are checked one by one against the manifest's chunk index (a damaged segment header or footer with intact chunks is framing damage; the data is intact). WAL records are read with resynchronisation (9.2). Torn tails follow 9.6, the segment set follows 9.8. The commits a damaged WAL region lost are those between the valid commits around it; if none are missing, the region held a Mark or Checkpoint record. Damage to one copy of redundant metadata (one GRAPH copy, one manifest fixed part of the latest snapshot) is a warning, not damage.

13.3 Maintenance mode

A read-write open whose load fails with damage (a checksum, a gap, a lineage mismatch, a missing file, both GRAPH copies invalid, container damage, 14.4) does not fail and does not repair: the store opens read-only with a damage report that lists the damaged files, chunks and records, the id ranges and commits affected, and for each its donor: an older snapshot whose chunks cover the id range plus the WAL up to the damaged one; a later snapshot that covers a damaged WAL record; or the other copy. The readable state is built from donors. Nothing is written in maintenance mode (no state change in GRAPH, no torn-tail cut).

Damage found while a store is open. Damage a writer finds in its files while it holds the store open (a backup, 12.6; a checkpoint's merge, 12.3; a verification, 12.9) follows the store's damage policy (5.2 bit 5), fixed when the store was created:

  • maintenance (the default): the store turns read-only for the rest of the time it is open, with the damage as the reason: every commit, mark, checkpoint, prune, rollback and compaction is refused, and nothing more is written (a close syncs the WAL and does not rewrite GRAPH, so the next open sees an unclean close, which is no damage). Reading and a backup from memory (12.11) go on.
  • continue: the store keeps accepting commits; the damage stays reported for as long as it is open.

The policy does not apply to damage found when the store is OPENED: that is always maintenance mode, as above. Problems of attic entries alone (history moved aside, 11.2) are reported by verification but do not count as damage of the store's own history.

13.4 Repair

Repair is explicit and never in place; it writes a new, verified store elsewhere:

  • The base is the newest snapshot with a readable manifest; its schema comes from schema.json, else an older snapshot's plus the WAL's schema changes. Its catalog of definitions comes from its manifest (covered by the variable part's CRC); when a definition there does not decode, from an older snapshot's catalog plus the WAL's op 10 changes up to the base, else it is lost (reported). The repaired snapshot carries the catalog, unknown definitions byte for byte.
  • A damaged chunk is rebuilt from the newest older snapshot whose chunks overlapping its id range are all intact, provided the WAL between the two is complete: that range's elements are decoded and every WAL mutation naming an element of the range is replayed. Edges of intact chunks whose endpoint is lost are lost elements.
  • The WAL after the base is replayed mutation by mutation: a damaged record is skipped when a later snapshot covers it; otherwise replay continues after the gap, and every element whose current state does not match a later mutation's before image (or whose mutation fails) is reported as diverged (the later value is kept), never guessed.
  • The result is a new lineage whose chain continues the damaged store's, with one snapshot named repaired. The report lists what was repaired, the lost commits, id ranges and elements, and the diverged elements. The damaged files are never changed.
  • The blobs the repaired state references are copied, each checked by length, CRC-32C and SHA-256 (the source is damaged); a missing or damaged one is reported as not carried and does not fail the repair. A fork and an attic fork (12.5) copy the blobs of their new snapshot's table the same way (length and CRC-32C).

Blobs are not store damage. A missing or damaged blob (4.6) never opens a store in maintenance mode, never freezes it under the damage policy and never makes a repair necessary: what needs its bytes fails (reading it, exporting it), everything else goes on. The writer reports it once per blob and failure in its operational journal (the reference implementation's blob.damaged record names the blob, the failure and a recommendation: any copy with the same hash, from a backup or another copy of the store, is the same bytes).

Bringing blobs back. Two operations of a CLOSED store (the writer lock) deal with missing or damaged blobs; neither changes the history:

  • A blob restore checks every blob of the referenced set (12.4: length, CRC-32C and hash) and copies each faulty one from another copy (a backup directory with its increments, a ZIP backup, a packed snapshot, another store) by its algorithm and hash, a blob of an unknown algorithm by its name (4.6): streamed into blobs/tmp-<random>, checked the same way, synced and renamed into place as a blob write (4.6). A healthy blob is never touched; a source blob that fails the check is not used.
  • A repair that drops faulty blobs (13.4 above, opt-in) leaves out of the repaired store's catalog every definition that references a missing or damaged blob, and the blob. It MUST be refused before anything is written while the current schema needs such a definition (a model a vector property's embedder names, 4.5).

14. The single-file container

A whole store in ONE file (extension .gstore by convention; the content decides): a log-structured container behind the backend abstraction of 4.3. The store's own files, names and byte formats are exactly those of a directory; the container only records which bytes a name holds. Nothing inside the file is ever overwritten, except the two header slots.

14.2 Writing

  • Every backend operation appends records: an atomic replace is one put record + sync; an append is one append record + sync; a truncate one truncate record + sync; name changes (mkdir, create, rename, remove) one record each, durable at the next sync. Bytes written through an open file handle are buffered (at most 1 MiB) and become one append record when the handle is flushed, synced, cut, full or dropped.
  • A new table is appended when the records since the last one reach max(16 MiB, 16 × the last table record's length), when the writer lock is released (a close), and after a damaged or missing table was found: table record, sync, the older header slot with generation + 1, sync. A torn table write leaves the previous header and table valid.
  • A new file is written under <name>.create-<hex>.tmp (preamble, an empty table as record 1, header slot 1 with generation 1), synced, hard-linked to the name only when nothing is there (a rename on file systems without links), and the directory synced.

14.3 Opening

The header slots are read; the valid ones are tried newest generation first: the table record a slot points at MUST be a type-8 frame with that sequence number and length, an intact payload CRC and a valid table. The first one that works is the base; the records after it are replayed. A damaged slot or table is a warning: the older generation and the records after it give the same names, because every change is a record. Without any usable table every record from offset 12288 is replayed (a warning).

14.4 Torn tail and damage

Replaying from the base, at a position p:

  • fewer than 44 bytes, or a header whose CRC is valid but whose payload runs past the end: the torn tail of an interrupted write;
  • an invalid frame header (marker, type, non-zero padding, fields length, header CRC, a durable end above p, or a sequence number below the expected one): the next position with a valid frame header is searched. None: if every byte from p on is zero, a torn tail; otherwise damage. Found at q: if the last valid frame of the file names a durable end above p, the bytes p..q had been made durable and are damage (replay continues at q; a sequence gap is reported as lost records); otherwise nothing after p was ever made durable: a torn tail at p;
  • an intact header with a payload CRC mismatch: an append whose bytes were made durable (a later frame names a durable end above p) is applied as it is and reported as damage; the last append of the file is applied as it is without a report (the store's own checksums judge it, as on a directory: zeros at the end of a WAL segment are a WAL torn tail, other bytes WAL damage); a put or another record made durable is skipped and reported as damage (a put keeps the old content); a table made durable is skipped with a warning (redundant); anything not made durable is a torn tail at p;
  • a valid record whose sequence number is above the expected one: damage (lost records);
  • an append beyond a file's end (a lost earlier append) leaves a hole and is damage.

A torn tail is cut (truncate + sync) at the next write, never by a reader. Container damage opens the store in maintenance mode (13.3); the container then refuses every write. Damage of both header slots or both tables alone loses nothing.

14.5 Locks, processes, relocation

  • The writer lock is the operating system's lock on the container file itself, held on its own handle; after taking it, the path MUST still name the locked file (a compaction may have replaced it), else it is taken again. A process without the writer lock changes the file only under that lock, taken for the one change.
  • A process that does not hold the writer lock compares the file's identity and length before each operation and replays what another process appended (or reloads a replaced file). A backup pin freezes the pinning process's view: every byte it references stays where it is until a compaction, and a replaced file stays readable through the open handle.
  • The file holds no path; it may be moved or copied while no process has it open. Temporary files of an interrupted create or compaction (<name>.create-*.tmp, <name>.compact-*.tmp) are removed when the writer lock is taken.

14.6 Compaction

A removal frees space only inside the file. Compaction copies the live state into <name>.compact-<hex>.tmp next to the file: the preamble, one mkdir record per directory, per file one create record (empty) or append records of at most 64 MiB, the table, header slot 1 with generation 1; synced; the writer lock is moved to the new file; the new file is renamed over the old one and the directory synced. It needs free disk space for the live data meanwhile and is refused on a damaged container.

Space accounting: total = the file's size; live = what a compaction would write, from the in-memory table; garbage = total - live (old tables, replaced and removed files, the framing of many small appends).

15. Versioning

  • Every file starts with a magic and a format version. There are three version axes: the store format version in GRAPH (offset 8, 5.1), the file format version in the manifests, segments, WAL segments and packed snapshots, and the single-file container version (14.1). This specification is store format version 4, file format version 4 and container version 1.
  • Version history of the store format: 1, the first version; 2 (Graphersal 0.1.0) added the store identity store_id at GRAPH offset 100 (5.5), which version 1 left zero; 3 (Graphersal 0.2.0) has the layout of version 2 and marks a store written with file format version 2. The bump exists for older readers: a reader of store format version 2 knows only file format version 1 and would take the manifests and WAL segments of file format version 2 for damage (an unknown version word is damage there, 13), open the store in maintenance mode and offer a repair that loses data; with version 3 in GRAPH it refuses the store as newer before it reads any other file. 4 (Graphersal 0.5.0) has the layout of version 3 and marks a store whose embedding models are blobs referenced by catalog definitions (4.5, 4.6), with the blob ledger (10.1) and the system journal (4.7); a version 3 store of Graphersal 0.4.0 may keep models as files under models/, which the upgrade migrates (15.1). With version 4 in GRAPH, Graphersal 0.4.x refuses the store as newer.
  • Version history of the file format: 1 (Graphersal 0.1.x); 2 (Graphersal 0.2.0) added the temporal value tags 9 to 13 and the vector value tag 14 (3); 3 (Graphersal 0.3.0) added the nanosecond temporal value tags 15 to 20 (with offsettime and the zone name of a datetime) and writes every temporal kind but date with them; 4 (Graphersal 0.5.0) adds the blob reference value tag 21 (3), the manifest's blob table (6.2 item 5), the segments of the system journal (4.7) and the Commit part record type 4 of the WAL (9.2, 9.3.1), written for commits larger than one part. Nothing else differs between these versions, so a reader of version 4 reads files of versions 1 to 3 as they are: a packed snapshot written by an older release loads, and a store created from it keeps its older manifest and segment files byte for byte (8, 12.1). Every file carries its own version: a snapshot MAY reference (6.2) or a packed snapshot MAY contain segment files of older versions, and a manifest of an older version MAY be rewritten in the current version (its content is valid in both). A file of a newer version is not readable by an older reader: since 0.1.1 every reader checks every file header first and refuses a store, backup or packed snapshot holding one as written by a newer version (unsupported version, below), never as damage. That is why file format versions 3 and 4 need no new store format version of their own, unlike version 2 (whose readers, 0.1.0, took an unknown file version for damage); store format version 4 marks the model migration (above). The container is still at version 1.
  • A writer writes only the current version.
  • A file with a newer version than the reader knows MUST be refused (unsupported version), never guessed at. A reader of file format version 4 MUST accept versions 1 to 4 in every file header (manifest 6.1, segment 7.1, packed snapshot 8, WAL segment 9.1).
  • A version from the future is not damage, and a store holding one MUST NOT be worked on. A file whose magic matches and whose header checksum is valid (the GRAPH fixed part, 5.1; a manifest fixed-part copy, 6.1; a segment or WAL segment header, 7.1, 9.1) but whose version word is above the reader's is "written by a newer version". The reader MUST refuse the whole operation with an unsupported-version error and MUST NOT classify it as damage (13). A store, backup or single-file store holding even one such file MUST NOT be worked on in any way: no write, no lock, no maintenance mode, no salvage or repair, no upgrade (15.1), no checkpoint, no backup into or out of it, so a reader can never corrupt what a newer writer wrote. A single-file container (14.1, whose preamble has no checksum) is newer when its magic matches and its container version is above the reader's. A header whose checksum fails stays damage. Every operation on an existing store, backup or attic checks, before it takes a lock, reads data or writes: the container version, then both GRAPH copies (either one newer refuses the store, whatever the other holds), then the headers of every manifest, snapshot segment and WAL segment of the tree (snapshots, holders, tmp-* directories and attic entries); a header it cannot read is left to the operation's own checks. A restored ZIP backup that is refused this way is removed again. (The reference implementation does so since 0.1.1.)
  • Format versions move only with a release that needs them. A patch release (x.y.Z) MUST NOT change any format version (store, file or container). A format version changes only with a release whose new features need it; a release that changes no format reads and writes the stores of the release before it as they are, with no upgrade.
  • A GRAPH of an OLDER store format version (its magic and fixed-part checksum valid, the version word below the current one) MUST be classified by its version word before any field that version did not have is checked: it is neither damage (13) nor "not a store". Every operation refuses it with "older format" (open, read-only open, info, verify, backup, restore of a backup directory, fork, conversion), except the upgrade (15.1), the repair (which reads a store of a released older version as upgraded and writes the repaired store in the current version) and the restore of a ZIP backup (which upgrades what it unpacks).
  • Every release reads every released version. A reader of store format version 4 MUST read the files of store format versions 2 (Graphersal 0.1.0) and 3 (0.2.0 to 0.4.x) and of file format versions 1 to 3, and a later version MUST keep reading them; a store of a released older version is upgraded without the build that wrote it (15.1). Store format version 1 was never released: a store of it is migrated through a packed snapshot exported by the build that wrote it, from which the current build creates a new store (only the graph state, schema and catalog move; marks, the attic and backups do not).
  • New value tags, record types, mutation ops, INTENT operations and flag bits require a new version, except flag bits that a reader may ignore without misreading the store (a writer preserves unknown bits it read).

15.1 Upgrading a store

Which store format versions an implementation upgrades, and how, is an explicit table; an upgrade not in it is refused before anything is written. The reference implementation's table (generated from its code):

"Version word" means only the version word of GRAPH and GRAPH.copy (and their checksums) changes, which is safe in place; "migration" means the version word plus the migration of the embedding models a version 3 store keeps under models/ (below; a store without models/ changes only its version word), in place or into a copy; "into a copy only" means the upgrade writes a new store and an in-place upgrade is refused; "unsupported" means the migration through a packed snapshot (below). A store holding a file of a newer version is never upgraded (15).

An upgrade converts a store of store format version 2 or 3 (a store, a backup directory, either backend) to version 4. Version 4 has the layout of versions 2 and 3 and every file of them is a valid file of version 4 (its own header names its file format version, which a version 4 reader reads), so an upgrade:

  1. Takes the writer lock of the store and refuses it while held (an older writer has it open).
  2. Checks every model of models/ against its manifest (4.5 "Older stores": every file's size and SHA-256, the three identity files, the weights' safetensors header) WITHOUT writing; a damaged, incomplete or unconvertible model refuses the upgrade.
  3. Verifies the store as version 4 would read it (12.6's checks: both GRAPH copies, every snapshot, every WAL record and the segment set of 9.8, the attic) WITHOUT writing: the GRAPH copies are read with the version word replaced by 4. Any problem refuses the upgrade (repair it instead, 13).
  4. With models/: writes INTENT upgrade_models (11.1).
  5. Rewrites GRAPH.copy, then GRAPH (each atomically, 5.3) with version 4 and every other field unchanged (lineage, identity, flags, the backup marker, wal_head, closed_at, wal_cut). Without models/ no other file changes, so no INTENT is needed: after a crash between the two writes the copies differ by the version word only and a version 4 reader uses the valid copy (5.3); repeating the upgrade rewrites both. An older reader refuses either state as newer.
  6. With models/: completes the INTENT (11.1): each model becomes ONE blob, the model tar of 4.5 holding its files and a manifest of format 3 built from the old one (identity, repository, revision, commit, licence, licence text, base models, gated, the files); ONE catalog commit (12.12, in a new WAL segment) defines the models (kind 5, no default); models/ is removed. The repository of a definition is the old manifest's; a model without one, or a second revision of a repository another model of the store takes, gets local/<12 hex> (its identity changes; the schema's embedder naming the old identity is renamed in the same commit). The positions before the migration commit have no models. A reader of version 4 that finds the INTENT completes it at its next read-write open or upgrade.

An upgrade into a NEW location copies every file of the store (as a conversion does: name by name, without the locks and temporary files) after step 2, writes a marker upgrade-in-progress.tmp into the target first, verifies the copy with its new GRAPH held in memory, then writes GRAPH.copy, GRAPH and removes the marker: until GRAPH is written the target is not a store, and a target holding the marker is an interrupted upgrade that the next upgrade into it clears. Unlike a conversion, the copy keeps the store id: it is the same store in the new version.

After an upgrade the files of file format version 1 stay where they are: snapshots, WAL segments and the attic keep their bytes, so the history is exactly what was written. A writer MUST NOT append to a WAL segment of an older file format version: when the newest segment of the lineage is older, the next record goes into a new segment of the current version (9.8: wal_head names it); a segment of an older version that holds no record (it starts at the next commit) is replaced whole by one of the current version under the same name.

A new FILE format version alone needs no upgrade and no table row: a store of store format version 3 written by 0.2.x (files of version 2) was opened and continued as it is by a reader of file format version 3 (Graphersal 0.3.x); its version 2 files stay, the files written from then on are of version 3 (a new WAL segment, new snapshots), and from then on 0.2.x refuses the store as newer (15).

  • New definition kinds (6.3), new payload keys of a known kind, new segment kinds (7.5) and named extra files (8) do not change the version: the rules of 16 tell every reader how to treat what it does not know.

16. Extensibility

The format is meant to grow without migrations. These rules bind every reader and writer of store format version 4 and file format version 4:

  1. Length before payload, payload as a map. Every definition carries its length before its payload (6.3), so a reader skips an unknown kind by its length; a payload is a property map, so a reader ignores unknown keys of a known kind. A new field is a new key, never a new layout. Payload keys are never kind, name or flags (6.3).
  2. Unknown, not critical: kept. A definition of an unknown kind without the critical flag is kept as opaque bytes (kind, flags, name, payload) and written back unchanged at the next checkpoint and in every copy (fork, backup, ZIP, repair), so an older reader never drops a newer definition. Unknown keys of a known kind are kept the same way (their values, written after the known keys in the order read).
  3. Unknown and critical: read-only. A critical definition of an unknown kind, or a file of a critical unknown segment kind (7.5), must stay consistent with the data (an index, for example); a writer that does not maintain it would corrupt it. A store holding one opens read-only for that reader (12.1), and a writer never stores such a definition itself (9.3).
  4. One WAL op for every kind. Op 10 (9.3) carries every definition change; a new kind needs no new op and no new version. Its replay follows rules 2 and 3.
  5. Large data in files of its own. The manifest is read whole and bounded at 256 MiB: a feature with large data stores a definition in the catalog plus files in the snapshot directory, referenced from the segment table by a new segment kind (7.5) with the same critical/ignorable rule; packed snapshots carry such a file as a named extra file (section kind 5, 8).
  6. Two version axes. The format version (the byte structure; with rules 1-5 it rarely moves) and content versions such as a saved query's dialect: a DSL evolves by compiling the stored text, never by re-encoding files.
  7. Upgrades without the older build. Every release reads every released store and file format version (15), so a store of a released older version is upgraded by the current build itself (15.1); a store format change keeps that possible. A packed snapshot of an older file format version loads as it is.
  8. Host kinds. Definition kinds 128-255 (6.3) belong to hosts, the applications built on a library that implements this format; the format never assigns them, so a host entity never collides with a future library kind. To the library a host kind is an unknown kind: kept as opaque bytes under rules 2 and 3 (a critical one opens the store read-only), never damage. A host SHOULD encode its payload as the property map of 6.3 (the reference implementation offers that codec publicly), so the payload stays inspectable and extensible by key.
  9. An unknown value of a known key is not damage. Damage is what a checksum, a length or the byte structure (value tags, record types, mutation ops, guarded by the format version, 15) says is wrong. Content behind a valid checksum that the reader cannot interpret was written by a newer writer, and a reader MUST NOT report it as damage or offer a repair that would drop it (a repair by a reader that cannot read it loses it):
    • in a definition payload (6.3): kept and not served (an unknown value it can represent), or kept opaque (a payload it cannot read as its kind at all); a critical one opens the store read-only (rule 3);
    • in the graph schema (schema.json, 6.1; a schema image of op 9, 9.3): the schema changes what writes are allowed, so it is never ignored. A reader opens the store READ-ONLY (the data without the schema; nothing is written, not even a torn-tail cut) and refuses every operation that would write a state derived from it (a checkpoint, a fork, a repair) as unsupported; a backup copies its bytes as they are; verify reports it as a note, not a problem;
    • an INTENT operation (11.1) or a GRAPH state value (5.1) the reader does not know, and a well-formed entry outside its layout in a backup archive (12.8): refused as unsupported, never damage.
  10. Side areas of the store. A directory at the store root that a reader does not know (as models/ is for a reader older than 4.5) is left alone: never listed as damage, never removed by a prune or a compaction, not copied by that reader's copies. A new side area therefore needs no new version when an older reader ignoring it cannot misread the store; the copies it misses are listed with the area (4.5). journal/ and INSTANCE (4.7) are such areas for a reader older than 4.7 (it refuses a store whose journal segment has a newer file format version through the header walk of 15, like any newer file). blobs/ and ledger (4.6, 10.1) are side areas too; a store referencing a blob holds files of file format version 4, which an older reader refuses as newer.

17. Conformance notes

Readers

  • Check every CRC before using the bytes it covers; check every count and length against the remaining input before allocating (2).
  • Never treat damage as a torn tail: apply 9.6 and 14.4 exactly. Never skip an unknown record type, value tag or mutation op.
  • Keep what you do not know (16): an unknown definition byte for byte, unknown payload keys of a known kind, an unknown value of a known key (not served, written back as read), an ignorable file of an unknown segment kind in every file-level copy; open a store with something critical you do not know, or a graph schema you cannot parse, read-only. Content behind a valid checksum that you cannot interpret is never damage (16 rule 9).
  • Replay only files whose graph_id is on the lineage chain, each ancestor only up to its branch point (5.4), and require commit continuity (9.7).
  • A read-only reader of a store MUST NOT write anything into it, take the writer lock, or cut a torn tail. It SHOULD take the shared backup pin while it copies files, so that a prune cannot remove them meanwhile.
  • A reader tailing a live WAL (CDC) reads only complete records with valid CRCs and treats an incomplete record at the end as "not yet written". Records before the writer's durable end are final; a record after it may still be cut off (9.7).
  • Read every file with the version in its own header (15): accept files of format versions 1 to 4 in one store or packed snapshot, reject a temporal value tag in a version 1 file, a nanosecond temporal value tag (15 to 20) in a version 1 or 2 file and a blob reference (tag 21) or a Commit part record (type 4) in a file of version 1 to 3, and reject a temporal value outside its range (3) as damage; a zone name you do not know is unsupported content (3).
  • Assemble a commit in parts (9.3.1) as ONE commit at the position of part 0; grow its body part by part, never from body_length up front; an incomplete commit in parts at the end of the last segment is a torn tail starting at part 0 (9.6).
  • Check a blob's length before reading it and its CRC-32C on every read; a missing or damaged blob fails only what needs its bytes and is never damage of the store (4.6, 13.4). Treat the content of a blob (a model tar, 4.5) as untrusted input.
  • Treat marks and ledger as derived from the WAL (10, 10.1) and the system journal as information only (4.7): a damaged or missing one is rebuilt or shown as a note, never damage, and nothing is decided from the system journal.
  • A store whose current schema needs a model (4.5) is opened only with that model loaded, or read-only by a reader that cannot run models; a needed model that is missing, damaged or does not fit refuses the open.

Writers

  • Write every new file with the current file format version (4) and GRAPH with store format version 4; never append a record to a WAL segment of an older file format version (start a new segment, 15.1), and never write a nanosecond temporal tag into a file of version 1 or 2.
  • Write a commit whose body is larger than the part size in parts (9.3.1): consecutive records of one segment, rotation only before part 0, one sync after the last part, and a failed part cuts the WAL back to part 0 (9.7, 9.9).
  • Write a blob completely (temporary name, sync, rename, directory sync) BEFORE the commit that references it, and remove a blob only when no retained history references it (4.6, 12.4).
  • Never copy instance data (WORKLOAD except into an upgraded copy, INSTANCE, the locks) as part of another store (4.4, 4.7); never write the system journal of a read-only store or of a store in which damage was found (4.7).
  • Take every commit, mark and checkpoint time and every system-journal time from the instance clock (18).
  • Follow the write ordering of 9.9: a WAL never holds a commit that did not happen, and a caller never gets "ok" for a commit that is not durable under the configured durability.
  • Make files visible only when complete: a temporary name, sync, an atomic rename, a sync of the directory. Verify a snapshot before it is renamed (12.3).
  • Write GRAPH as specified in 5.3, wal_head as in 9.8, and every multi-file change under an INTENT with idempotent steps (11.1).
  • Never remove WAL or snapshots implicitly: only an explicit prune (12.4), a rollback (12.5) or removal of an attic entry removes history.
  • Record only store-relative names (4.2).

18. Time: the instance clock

Every time a store's history holds (commits, 9.3; marks, 9.4; checkpoint records, 9.5) and every time of the system journal (4.7) is read from ONE clock per instance (a process that has the store open, or a closed-store operation, 12.12):

  • Reading. A reading is max(system clock, floor) in microseconds (section 2) and raises the floor to itself, so readings never decrease (two readings may be equal). A commit's time is at least the time of the commit before it, and a record about commit N (a mark, a checkpoint, a journal record) is never earlier than commit N.
  • The floor is not stored. When an instance opens a store, or a closed-store operation starts, the floor is raised to the latest time the store's files hold: the loaded snapshot's times (6.1: created at, last commit at), every commit, mark and checkpoint record of the replayed WAL, and the newest record of the system journal. A recovery to a target (12.1) raises it from what it read; a read-only view of a past position uses the store's full floor.
  • A system clock that steps back (a resumed virtual machine, a manual change) leaves every time at the floor until the system clock passes it again; a step of more than one second is reported (the reference implementation writes a clock.step_back journal record). Times therefore stay monotonic, and the target "the last commit at or before time T" (12.1) stays well defined.
  • Times that are not part of the history (the "created at" of a snapshot manifest, a WAL segment header, the times of GRAPH, backups and attic entries) are informative and read from the system clock.
