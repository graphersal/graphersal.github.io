The Graphersal Documentation

Serving Layers

A server that hosts one product graph for many customers keeps the product once and gives each customer a layer over it. Clients configure a name such as /mcp/acme, never a version. When the product is released again, the server publishes new layers over the new product version, and the name moves to them. This page describes that serving model, which pieces Graphersal provides for it, and what a host builds itself.

graphersal-serve hosts one graph per process, and it stays that way: it has no base pool, no catalog of names and no multi-graph server. A host builds those on its extension points. A complete reference host lives in the tests of graphersal-serve, in the module extension_tests::reference_resolver (crates/graphersal-serve/src/extension_tests.rs). The excerpts on this page come from it.

The serving model

  • Base pool. The server loads each product version once, as a frozen LayerBase, and keys it by its identity (BaseRef). product@2026.3 and product@2026.4 live side by side while layers over the old version still exist.

  • Catalog. Each served version is named <name>@<version> and is a layer over a pooled base:

    product@2026.3   -> base (served read-only as an empty layer over it)
acme@2026.3      -> layer over product@2026.3
globex@2026.3    -> another layer over the same base
acme             -> alias, now acme@2026.3
acme@2026.2      -> explicit pin to an old version, kept on purpose

  • Sessions are pinned. An MCP session is bound to a graph when it starts (initialize) and stays on that graph for its whole life. A release flips the alias: new sessions get the new version, and open sessions finish on the old one.

  • Old versions are retired. Once no alias and no pin names a version, and no session has used it for a while, the host drops it. When a base has no layers left, the host drops it from the pool.

Base identity

Every read-only open of the same commit has the same BaseRef, and so does a .gsnap export of that commit's snapshot. A second load of a pooled commit can be dropped in favour of the pooled base. A commit to the base store makes a new identity, so each product version is its own base.

A .gsnap export copies the store's newest snapshot. Commits that are still only in the write-ahead log are not in it, so checkpoint before you export a release. Otherwise the export holds the commit of the newest snapshot, with that commit's identity.

Samples and GraphSON or GraphML files get a new lineage id at every load. They never count as the same base twice, so a server should load its bases from a Store or a .gsnap.

This example pools two product versions loaded from one versioned store and lays two customers over the same base. It needs only the graphersal crate:

use std::collections::HashMap;
use std::sync::Arc;
use graphersal::persist::{MemDir, RecoveryTarget, Store, StoreOptions};
use graphersal::prelude::*;
use graphersal::storage::{BaseRef, LayerBase};

// The release process: one base store, a mark per product version.
let dir = MemDir::named("product");
let store =
    Store::create_with(&dir, TraversalGraph::tinkerpop_modern(), StoreOptions::new()).unwrap();
store.mark("2026.3").unwrap();
GraphTraversalSource::new(&mut *store.graph().write()).add_v("feature").iterate().unwrap();
store.mark("2026.4").unwrap();
store.close().unwrap();

// The server's pool: one LayerBase per base commit.
fn pooled(pool: &mut HashMap<BaseRef, LayerBase>, dir: &MemDir, mark: &str) -> LayerBase {
    let loaded = LayerBase::from_store_read_only(dir, RecoveryTarget::Mark(mark.into()))
        .unwrap()
        .with_name(format!("product@{mark}"));
    let key = *loaded.base_ref().unwrap();
    pool.entry(key).or_insert(loaded).clone()
}
let mut pool = HashMap::new();
let acme = pooled(&mut pool, &dir, "2026.3").new_layer().unwrap();
let globex = pooled(&mut pool, &dir, "2026.3").new_layer().unwrap(); // the pooled base
assert_eq!(pool.len(), 1);
assert!(Arc::ptr_eq(acme.read().base(), globex.read().base()));
let next = pooled(&mut pool, &dir, "2026.4").new_layer().unwrap();
assert_eq!(pool.len(), 2);
assert_eq!(acme.read().vertex_count().unwrap(), 6);
assert_eq!(next.read().vertex_count().unwrap(), 7);

The route tag

At an HTTP initialize, the endpoint asks the context for its route. If the context has one, the session id becomes <route>~<id>, for example acme@2026.3~9f2c…:

  • With signed ids (Mcp::with_session_key), the route is part of the signed data. A changed, removed or added route breaks the signature, and the endpoint answers 404. Replicas that share the key verify each other's ids, so a load balancer may send a session's requests to any replica.
  • In table mode (the default), the table stores the whole routed id. An edited route is an unknown id, which is also a 404.
  • A route is 1 to 128 bytes of [A-Za-z0-9._-@/:+=] (is_valid_session_route). An invalid route makes initialize fail with a JSON-RPC error, so a session is never left unpinned.

A stream connection (Context::mcp_connection) is its own session and has no route: the host picks the context when it opens the stream.

Sessions belong to their identity

Every HTTP MCP session belongs to the identity of the request that sent its initialize (what the host's request filter attached, McpRequest::with_identity; none means anonymous). A request that names the session id with another identity gets the same 404 as an unknown session, and a DELETE from it ends nothing. Anonymous counts as an identity of its own: an anonymous session cannot be used by a signed-in caller, and the other way round. In table mode the table stores the identity with the session; with signed ids the identity is part of the signed data (an anonymous id signs exactly what it signed before). One Mcp shared by several routes (/mcp and per-graph paths) accepts a session id on each of them, for its identity only. A resolver that checks a routed id for a caller uses mcp.verified_session_route_for(id, identity); verified_session_route(id) checks it as anonymous.

Runs belong to their identity

The page id a browser sends (X-Graphersal-Client) is chosen by the client, so it cannot own a run alone. When the host's request filter attaches an identity (Request::set_identity), every run, the Stop of a page (POST /api/cancel), MCP request cancellation and the fairness key of a host's job queue use the identity together with the page id: a caller with another identity, or an anonymous one, that sends the same page id cancels nothing. The key is <length>:<identity>/ before the plain key (5:alice/page:tab; RunInfo::client, the run administration's client). Without an identity the key is the plain one, as in the CLI's dev server. The run administration (ContextBuilder::admin_runs) keeps its own rules: it lists and cancels runs by the registry's id, whatever their identity.

The change feed (GET /api/changes) names who made a change (recent[].by, detail) only to a request of the same identity; a change made under another identity, anonymous included, reads by: "another identity" without detail, so a reader learns no other principal's page id. Without identities every change is shown as before.

Sessions survive a restart

By default the session table lives in memory: a restarted host forgets every MCP session, and each client gets 404, initializes again and, in directory mode, selects its graph again. A host that wants the sessions back after a restart gives the endpoint a store:

let mcp = Mcp::new(false, None, false)
    .with_max_sessions(1024)                     // first: the load keeps the newest 1024
    .with_session_store(Arc::new(MyFileStore::new(dir)))?;

SessionStore has two methods: load answers the stored sessions once, and save gets the whole table after every change (a session created, a graph selected, a selection renamed or its note told, a session ended or evicted). A save runs outside the table lock, one at a time, and never writes an older table after a newer one. A failed save is a tracing warning; the request goes on and the next change saves again. So write atomically (a temporary file, then a rename).

Each row is a StoredSession: the SHA-256 of the id (64 hex digits; the table never holds the plain id, so the store holds nothing a client could present), the identity, the selected name, the old name of a pending rename note, the negotiated protocol revision, the client's {name, version} and the creation time in Unix seconds. The host serialises it in any format (strings, a number and a JSON value) and rebuilds it with StoredSession::new. A restored session answers its old id for the same identity only, with its selection and its pending note. The expiry rule is unchanged: at most with_max_sessions, the oldest dropped first.

When the host revokes a user's token or removes the user, mcp.forget_sessions_of(Some(id)) ends that identity's sessions at once (and saves the table); it answers how many it ended. Signed ids (Mcp::with_session_key) keep no table: with_session_store refuses them with an error, and forget_sessions_of ends nothing there.

Read-only requests

A host that gives some callers read access only marks their requests: request.mark_read_only(), in its router or its RequestFilter, after it decided who sent the request. The mark holds for that one request, and nothing clears it. graphersal-serve then serves the request like this (the context itself stays writable for every other request):

  • POST /api/execute and POST /api/query run under the reading authorizer. A script or saved query that would write fails with a permission error and changes nothing.
  • Every other route that writes answers 409 with the graph is served read-only: writes are refused. This request has read access only: ask for write access to change the data. (READ_ONLY_HEADLINE, READ_ONLY_REQUEST_HELP). That covers the schema, element, catalog, compression, index and saved-query writes, the scheduled jobs, the advisor's apply, dismiss and restore, POST /api/save, and every Store operation that writes: checkpoint, mark, rollback, the attic, compaction, and also fork, backup and view, which write directories or switch the view every client of the context sees.
  • Reads stay open, downloads included: exports in every format, the .gsnap download, Store snapshots, statistics, the journal, the layout.
  • /mcp serves the request under the context's MCP profile made read-only (Profile::with_read_only(true) in graphersal-mcp): only reading tools, and a writing query is refused. The same MCP session may write again on a request that is not marked.
  • GET /api/info and GET /api/changes answer readOnly: true for the request, and so does their mcp status.

The host's own extra routes (Hooks::route) see the mark with request.is_read_only() and decide for themselves. A host that serves MCP in directory mode (handle_directory) answers a reader's profile from its GraphDirectory::host instead.

Query limits at run time

launch (and ContextBuilder::presets) take the session presets: the traversal options every run gets (evaluationTimeout, traversal.max_traversers, ...), the Rhai limits, the script budget and whether the limits are ceilings (SessionPresets::with_ceilings). A host changes them on a served context without reloading the graph:

let presets = SessionPresets::new()
    .with_option("evaluationTimeout", ElementProperty::from(10_000_i64))
    .with_ceilings(true);
context.set_presets(presets)?;
  • Every run that starts after the call runs under the new presets: a query of the HTTP API, an MCP tool call (also in an MCP session opened before), a scheduled query handed out later. This holds on the session thread and on every worker of a host's JobQueue.
  • A run that is already running keeps the presets it started with. The call does not wait for it: each session applies the change just before its next job.
  • GET /api/info presets, Context::presets() and the statistics answer the new presets.
  • Connections, MCP sessions, the graph and the Store stay as they are.

The process memory ceiling (memory.limit) is no preset; it stays a setting of the whole process. The CLI dev server never changes its presets.

File root

Without further settings a client with write access may name any path the server process can write: a backup job's directory, the directory of a Store fork or backup. A host that serves callers it does not trust with the machine's files sets a file root on each context: ContextBuilder::file_root(Some(root)). The default, None, keeps the old behaviour (the CLI dev server never sets one). With a root:

  • POST /api/jobs/define resolves a backup job's path under the root: a relative path is relative to the root, and a path that leaves it (an absolute path elsewhere, .., a symbolic link pointing out) is refused in the answer. The job stores the resolved path.
  • POST /api/catalog/load refuses with 403 a catalog with a job that writes outside the root, and loads nothing. A stored job path must be absolute and inside the root.
  • The dir of POST /api/store/fork, /api/store/attic/fork and /api/store/backup is resolved the same way: a relative dir is relative to the root (not to the store's directory), and one outside it answers 403 with paths must lie inside the server's file root. Without a dir the default directory next to the store is used, as before.

The root must exist; a requested dir under a missing root answers 500. Jobs already stored in a store the host loads (an imported, restored or cloned store) are not checked by the context: the host passes the store's definitions to graphersal_serve::jobs_outside_file_root and disables or refuses the jobs it returns.

What a host builds

The host owns four pieces: the pool, the catalog, the path rewrite and the resolver. It also decides when an old version goes.

Pool and catalog

struct Served {
    context: Arc<Context>,
    base: BaseRef,
    last_used: Instant,
}

#[derive(Default)]
struct Catalog {
    versions: HashMap<String, Served>, // "acme@2026.3" -> its context
    aliases: HashMap<String, String>,  // "acme" -> "acme@2026.3"
    kept: HashSet<String>,             // explicit pins, never retired
}

struct LayerHost {
    mcp: Arc<Mcp>, // one endpoint for every context
    pool: Mutex<HashMap<BaseRef, LayerBase>>,
    catalog: Mutex<Catalog>,
}

One context per version

Each version gets a session thread that serves its layer, and a context built with .layered(true), its route, the shared endpoint and a profile of its own. Here a read-only customer gets Profile::new(true).with_access_policy(AccessPolicy::read_only()).

fn publish(&self, version: &str, base: &LayerBase, profile: Profile) {
    let layer = Arc::new(base.new_layer()?);
    let name = version.to_string();
    let (jobs, ()) = spawn_session(
        SessionPresets::new(),
        move |session| session.load_shared(layer, &name, "layer").map(|_| ()),
        None,
    )?;
    let context = Context::builder(Runner::Session(jobs), host_check)
        .layered(true)
        .shared_mcp(self.mcp.clone())
        .mcp_profile(profile)
        .mcp_session_route(Some(version.to_string())) // "acme@2026.3"
        .build();
    self.catalog.lock()?.versions.insert(version.into(), Served { context, .. });
}

A customer layer that must survive restarts comes from a layer store instead (Store::<LayeredGraph>::open_layer(dir, &base, options)), and the session serves the store's graph. The layer store refuses a base whose BaseRef differs from the one it was created over.

Path rewrite

A context answers MCP at /mcp only. The host's listener turns POST /mcp/acme into POST /mcp and puts the name into a header. It drops any copy of that header the client sent, so only the path names the graph:

const GRAPH_HEADER: &str = "X-Graphersal-Graph";

let name = path.strip_prefix("/mcp/").filter(|name| valid_name(name))?; // else 404
let mut request = Request::new(method, "/mcp", body);
for (field, value) in client_headers {
    if !field.eq_ignore_ascii_case(GRAPH_HEADER) {
        request = request.with_header(field, value);
    }
}
server.handle(request.with_header(GRAPH_HEADER, name))

The resolver

The resolver runs for every request. A request with a session id goes to the version in the id's route, after two checks. A request without one, such as initialize, goes to the alias's current version, or to the version the path names (/mcp/acme@2026.2):

impl GraphResolver for LayerHost {
    fn resolve(&self, request: &Request<'_>) -> Result<Arc<Context>, HttpError> {
        let name = request.header(GRAPH_HEADER).ok_or_else(|| not_found())?;
        let routed = match request.header("Mcp-Session-Id") {
            Some(id) => {
                // 1. The endpoint knows the id (signature, or the table).
                let route = self.mcp.verified_session_route(id).ok_or_else(|| not_found())?;
                // 2. The route is a version of the name in the path.
                let belongs = if name.contains('@') {
                    route == name
                } else {
                    route.split_once('@').is_some_and(|(of, _)| of == name)
                };
                if !belongs {
                    return Err(not_found());
                }
                Some(route)
            }
            None => None,
        };
        let mut catalog = self.catalog.lock()?;
        let version = match routed {
            Some(route) => route.to_string(),
            None if name.contains('@') => name.to_string(), // an explicit pin
            None => catalog.aliases.get(name).cloned().ok_or_else(|| not_found())?,
        };
        let served = catalog.versions.get_mut(&version).ok_or_else(|| not_found())?;
        served.last_used = Instant::now();
        Ok(served.context.clone())
    }
}

A release publishes the new version and then flips the alias: catalog.aliases.insert("acme".into(), "acme@2026.4".into()). Nothing else changes. Sessions already open carry acme@2026.3 in their ids and keep reaching that version's context.

When to drop an old version

An open session keeps working only while the resolver still holds its version's context. The endpoint cannot tell the host when a session has ended: a client may never send DELETE, and a signed id stays valid for good. So the host decides. The reference host's policy:

  • A version is needed while an alias names it or it is in kept (an explicit pin).
  • A version that is not needed is retired after grace without a request (retire_idle). The resolver records last_used on every request it resolves. Retiring removes the context from the catalog. Its session thread then ends and its layer is dropped.
  • A session still routed to a retired version gets 404 for an unknown session. The MCP client then starts a new session, which gets the current version. Pick the grace period so that this rarely happens during a working session (minutes to hours, not seconds).
  • When no served version reads a pooled base any more, the base leaves the pool (evict_unused_bases), and its memory is freed with the last layer over it.

Other policies fit the same pieces: a deadline per release, a count of sessions per version kept by the host, or retiring only at night. The test a_retired_version_drops_its_context_layer_and_finally_its_base checks the reference policy: the context, the layer and finally the base are released.

One endpoint over all graphs (directory mode)

Instead of one MCP URL per graph (/mcp/acme), a host may offer a single endpoint that an agent's harness configures once. The host implements graphersal_mcp::GraphDirectory over its catalog:

  • list(): the graphs and aliases an agent may name, each a GraphEntry with its kind (plain, layer, base), state (unloaded, loading, loaded, needs-model, failed with a reason), read-only flag and description.
  • resolve(name): the route of a name, an alias resolved now (acme -> acme@2026.3). The endpoint calls it on every call of a session, so keep it cheap.
  • host(route): the context serving that route (a graphersal-serve Context is a graphersal_mcp::Host) and its MCP profile, or an error whose text the agent reads, such as database 'acme@2026.3' is not loaded; ask an operator to load it.

The methods take no caller. A host whose graphs differ per caller builds the directory for each request from the identity it attaches to that request, and passes that directory to handle_directory. It lists only what the caller may see, answers a hidden graph with exactly the error of an unknown name (from resolve, use_graph and the graph argument alike), and answers the caller's profile from host (read-only for a reader). The session's selected name is resolved through the directory of each request, and a session cannot be used by another identity (see "Sessions belong to their identity" above).

The host's listener passes every request to its endpoint path to mcp.handle_directory(&catalog, request). Inside an MCP session the agent calls list_graphs, selects a graph with use_graph {name} and may switch later; every data tool takes an optional graph argument that names another graph for one call. Each call runs on that graph's context under that context's profile, so its read-only flag and access policy apply. Saved queries are not tools of their own here: the agent runs them with run_saved_query (and graph).

  • The selection is a name. use_graph stores the name the agent asked for (a graph or an alias, spelled as list() spells it when one entry matches ignoring ASCII case) and the endpoint resolves it again on every call, as an HTTP path /db/<name>/ is. This is not the route tag above: a route tag pins a session to one version, a directory selection follows its name.

    • Re-pointed alias: the session follows it silently. Errors of the new target (not loaded, read-only) are ordinary tool errors.
    • Removed alias: a call fails with "pick another graph: list_graphs, then use_graph" only while no graph or alias of that name exists. The selection stays, so an alias created again under that name simply works on.
    • Renamed alias: the host renames it in its catalog, then calls mcp.rename_selection(old, new) (it answers the number of sessions moved). Each moved session's next tools/call answer starts with one line, note: alias "<first old>" was renamed to "<current>"; several renames before that call give one note from the first name to the current one.
    • A real graph name stays on that graph whatever the aliases do.

  • list_graphs answers selected (the session's name, or null) and selectedGraph (the graph that name resolves to now, or null); use_graph answers selected (the name) and graph (its graph now).

  • A new session starts empty. After a reconnect, or when the endpoint forgot the session (the table keeps MAX_SESSIONS, 64, unless Mcp::with_max_sessions says otherwise; the client then gets 404 and initializes again), calls that name no graph fail with a message that names list_graphs and use_graph, and the instructions tell the agent to select again.

  • Table sessions only. The selection lives in the session table, so a directory endpoint refuses signed session ids (Mcp::with_session_key).

  • Mcp::with_endpoint(path) sets the path Mcp::status shows.

  • The route is visible to the client. It is part of the Mcp-Session-Id header, so never put a secret, a tenant key or a storage path into it. A versioned name is enough.

  • Check the name in the path. A client that may use two graphs holds genuine session ids for both. Without the name check, an id that /mcp/globex handed out would reach globex's graph when sent to /mcp/acme, past any authorization that the host based on the path. The check is needed in both session modes: a signature proves the id is genuine, not that it belongs to this path.

  • Edited routes. In table mode an edited id is an unknown id, and with signed ids it fails the signature. Ask the endpoint (verified_session_route) before trusting the route. The plain session_route decoder does not check anything.

  • Ignore the client's copy of the routing header. The host sets the name header from the path and drops one the client sent.

  • Profiles are per context. The read-only flag and the access policy of each customer are in that customer's contexts (mcp_profile). One shared endpoint does not mean one shared policy.

  • Authentication stays the host's job, in a RequestFilter that knows the path's name. The filter attaches the caller's identity and, for a caller with read access only, marks the request read-only (see "Read-only requests" above).
