Releases and Versioning

Versioning

Graphersal follows Semantic Versioning. Before 1.0 a minor version (0.1 to 0.2) may break the API; a patch version (0.2.0 to 0.2.1) does not.

Every crate of the workspace shares one version number ([workspace.package] in the root Cargo.toml), and the Python package and the web playground are released with the same number:

Stability in 0.4.x

The same rules hold for every minor line before 1.0 (they held for 0.1.x, 0.2.x and 0.3.x as well); a minor release (0.3 to 0.4) may break them, and its release notes list every break with the upgrade step (Release Notes 0.4.0).

  • Stable within 0.4.x (additive changes only): the public API of graphersal outside the items marked EXPERIMENTAL, the DSL and the schema format.
  • EXPERIMENTAL (may change in any 0.4.x release): the GraphStorage trait and its associated types, PersistentStorage, AnyGraph, StoreDir, and graphersal-storage-tests; pin the exact version.
  • Internal: graphersal-session, the wasm crate's JS API, the dev server's HTTP API and its MCP tools (--server is a development tool, bound to the loopback interface unless --host or a container says otherwise), the experimental AI Chat.
  • The storage format has its own version numbers (Format Versions and Upgrade): a patch release never changes a format version, and every release reads the formats of every release before it (an older store is upgraded with graphersal store upgrade, no older build needed).

The API rules that keep a change additive (public enums and result structs #[non_exhaustive], default methods for every new trait method) are checked with cargo-semver-checks:

cargo install --locked cargo-semver-checks          # one-time
cargo semver-checks --package graphersal --baseline-rev <previous release tag>

From 0.1.0 on a reported break is a release blocker unless the version number says so.

Release gates

Before a version is tagged:

  • the CI workflow, started by hand with full (gh workflow run CI -f full=true: Linux and Windows), is green: format, clippy, every test suite incl. the TinkerPop suite, the feature and wasm32 matrices, the MSRV, the playground tests;
  • the checks CI leaves out pass locally: RUSTDOCFLAGS="-D warnings" cargo doc with the feature sets of CLAUDE.md, mdbook build book, and the TinkerPop suite on the foreign storage (GRAPHERSAL_TEST_STORAGE=forwarding);
  • cargo deny check (licences, RustSec advisories, duplicate crates, sources) passes against deny.toml;
  • the long fuzz budgets pass: robustness, the merge checkpoint and the verified backups (below; a fast budget of each runs in every cargo test);
  • a benchmark run on a quiet machine shows no unexplained regression against the previous release;
  • a dry run of the CLI binaries (gh workflow run "CLI binaries" --ref <release branch>, see Publishing) is green on all five platforms;
  • cargo publish --dry-run succeeds for every published crate, graphersal first, then the crates that depend on it;
  • the version's release notes (book/src/release_notes/, for 0.2.0 Release Notes 0.2.0) describe what changed; they are the project's record of changes (there is no separate CHANGELOG.md) and the text of the GitHub Release.

The long fuzz budgets (release builds with overflow checks and debug assertions kept on):

CARGO_PROFILE_RELEASE_OVERFLOW_CHECKS=true CARGO_PROFILE_RELEASE_DEBUG_ASSERTIONS=true \
ROBUSTNESS_CASES=500000 ROBUSTNESS_SEED=23 ROBUSTNESS_THREADS=7 \
  cargo test --release -p graphersal --features script,io,display,serde,persist,gql \
  --test all robustness_fuzz_tests::fuzz_long -- --ignored
ROBUSTNESS_INPUT_CASES=20000 cargo test --release -p graphersal \
  --features script,io,display,serde,persist,gql --test all robustness_input_tests::
MERGE_FUZZ_CASES=60000 MERGE_FUZZ_SEED=1 MERGE_FUZZ_THREADS=8 cargo test --release -p graphersal \
  --features script,io,display,serde,persist,gql,persist-zip --test all merge_checkpoint_fuzz_tests::
BACKUP_FUZZ_CASES=60000 BACKUP_FUZZ_SEED=1 BACKUP_FUZZ_THREADS=8 cargo test --release -p graphersal \
  --features script,io,display,serde,persist,gql,persist-zip --test all backup_fuzz_tests::

Robustness findings go to target/robustness-findings.txt (ROBUSTNESS_REPLAY=<seed> replays one case); a failing merge or backup case prints MERGE_FUZZ_REPLAY=<seed> or BACKUP_FUZZ_REPLAY=<seed>.

Benchmarks

cargo bench -p graphersal --bench graph --features io,script,display,serde is the regression benchmark. Every supported step or feature has at least one representative shape in crates/graphersal/benches/graph.rs, run on a graph large enough to surface an O(n²)-class regression (the 110k-element large graph), so a change that reintroduces an allocation- or complexity-class regression is caught by cargo bench rather than by a user profiling a real dataset. A new step gets its bench shape with the step. Benchmarks run once per release on a quiet machine and are compared with the previous release, not per change.

Publishing

  1. Tag the release commit: git tag -a v0.2.0 -m "Graphersal 0.2.0" && git push origin v0.2.0 (the tag equals the workspace version).
  2. The crates go to crates.io by hand, in dependency order: cargo publish -p graphersal, then graphersal-storage-tests, graphersal-session and graphersal-cli.
  3. The workflow release.yml, started on the tag: gh workflow run Release --ref v0.2.0. It checks that the tag matches the version and that the version's release notes exist, then runs two independent parts:
    • PyPI. It builds the five-platform wheels and the sdist through python.yml (which also runs the binding's tests and installs each wheel it can run), and uploads them with PyPI Trusted Publishing from the environment pypi (no token is stored).
    • CLI binaries and the draft GitHub Release. It builds the graphersal binary through binaries.yml with the dist profile (release + fat LTO + stripped symbols; never panic = "abort", units roll back on unwind), natively on each platform's runner: Linux x86_64 and aarch64 as static musl builds, macOS arm64 and x86_64, Windows x86_64. Each build is smoke-tested on its runner (--version, a query, the dev server's /api/info) and packed as graphersal-v<version>-<platform>.tar.gz (Windows .zip) with LICENSE-APACHE, NOTICE, README.md and THIRD-PARTY-LICENSES.html (cargo-about, about.toml). A final job writes SHA256SUMS and creates the GitHub build provenance attestations. The job github-release then creates a draft GitHub Release for the tag, titled "Graphersal ", with the five archives and SHA256SUMS attached; its text is the version's release notes (book/src/release_notes/release_notes_<version>.md) with the book links made absolute on graphersal.dev, the soft line breaks joined and a section about the prebuilt binaries added (.github/scripts/release_notes.py <version> prints the same text locally).
  4. Check the draft on the repository's Releases page: five archives (linux-x86_64, linux-aarch64, macos-arm64, macos-x86_64, windows-x86_64) plus SHA256SUMS; download one archive and check it (sha256sum -c SHA256SUMS --ignore-missing, gh attestation verify <archive> --repo graphersal/graphersal, unpack it and run graphersal --version); read the release text, its links included. Then publish the draft ("Publish release", or gh release edit v0.2.0 --draft=false). Only a published release is visible to users and to cargo binstall graphersal-cli (its metadata in crates/graphersal-cli/Cargo.toml names the same archives).

Before tagging, the binaries can be built as a dry run on any branch: gh workflow run "CLI binaries" --ref <branch> builds, smoke-tests and uploads the archives as workflow artifacts and publishes nothing (no attestations). -f compare_musl=true adds a job that times the same queries on the large graph with a glibc and a musl build of linux-x86_64 and writes the comparison into the run's summary.
