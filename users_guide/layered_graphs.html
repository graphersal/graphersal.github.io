The Graphersal Documentation

Layers

A layer is a writable graph over a frozen base graph. The base is loaded once and never changes. The layer stores only its own difference from it: the elements it adds, and the base elements it modifies or removes. To a query, a layer looks like an ordinary graph. Every step, saved query, schema rule and transaction works on it the same way, and nothing tells it apart from a graph that holds all of its data itself.

The typical use is a product graph shared by many projects. The product (the "box") is the base. Each project gets a layer, and the same indexer scripts that built the product fill it with the project's own repositories. Most of a project graph is the product itself, so a layer costs about what the project adds or changes, not a copy of the product. Several layers can share one base in the same process.

EXPERIMENTAL in 0.9.x. From Rust a layer can be saved as a layer snapshot and read back over its base, or kept in a layer Store (Store::create_layer / Store::open_layer); the CLI and the dev server keep a layer in a layer store with --layer-store, --layer and Python keep it in memory (see Limitations). How the storage works inside, its capabilities and memory figures are on the developer page Layered Graphs. A server that serves many customers' layers over shared product versions, one MCP endpoint per name, is described in Serving Layers.

Where an element comes from

Only some queries need to know whether an element is the product's or the project's. Three functions answer that question, and only when they are called. Everything else reads the layer as one graph.

FunctionExampleAnswer
layer()g.v().has_label("class").layer()the origin of each vertex or edge
has_layer(origins...)g.v().has_layer("added", "modified")only the elements with one of these origins
g.layer_diff(#{..})g.layer_diff(#{kinds: "vertex"})the whole difference against the base, as one map

An element has one of three origins:

  • "base": the element is the base's, unchanged. A base element written back to its base state, or written with a value equal to the base value, is "base" again.
  • "added": the layer created it.
  • "modified": a base element whose properties or labels the layer changed.

A removed base element cannot be traversed, so layer() never answers for it. It appears only in g.layer_diff(), under removed.

On a graph without layers (every sample graph, file and Store) all three functions still work: everything is "base" and the diff is empty. A query that uses them runs on both kinds of graph.

g.v().layer().dedup().to_list()   // ["base"]: the sample graph is no layer
g.v().has_layer("added", "modified").count().next()   // 0
g.e().has_layer("base").count().next()   // 6
g.v(1).out_e().group_count().by(__.layer()).next()   // #{"base": 3}
g.layer_diff()   // #{"added": [], "modified": [], "removed": [], "truncated": false}
g.layer_diff(#{kinds: "edge", labels: ["knows", "created"], limit: 10})["truncated"]   // false
g.v().has_layer("new").to_list()   // error: "new" is no origin (base, added or modified)

has_layer() without arguments keeps every vertex and edge; has_layer([]) keeps none, like has_label(). An unknown origin is an error before the query runs, even inside a child traversal no traverser reaches. Both steps accept vertices and edges only: anything else (a value, a property) is an error.

g.layer_diff(#{kinds, labels, limit})

g.layer_diff() returns everything the layer changed. All options are optional:

OptionValueDefault
kinds"vertex", "edge", or a list of themboth kinds
labelsa label or a list of labels; an element matches when any label of its base label set or its layer label set is in the list. [] matches nothingevery label
limita positive number of entries, counted across the whole diffno limit

The answer is a map:

KeyValue
addeda list of the elements the layer created: {kind, id, labels, properties}, an edge also with out and in (the endpoint ids)
removeda list of the base elements the layer removed, in the same form, with their base labels and properties
modifieda list of the base elements the layer changed: {kind, id, base_labels, labels, properties} (an edge also with out and in), where properties maps each changed key to {base, layer}; a key the layer added has no base, a key it removed no layer
truncatedtrue when limit left out further entries

An edge's labels is a list of one label. The diff lists vertices first (added, removed, modified), then edges in the same order; added elements are listed in creation order, except that an element created after a removal may fill the removed element's place. Values are the logical values, the same ones a query reads. In the DSL the keys of each map come out sorted (added, modified, removed, truncated), because the DSL's map type sorts them. The Rust form (LayerDiff::to_property) and Python keep the order of the table.

A g.layer_diff() in a script sees the script's own earlier writes. It reads the delta only, never every base element, so it is cheap on a large base with a small layer. It asks for Read on Data (see Permissions).

Memory: what a layer weighs

g.memory_usage() on a layer reports the layer's own footprint as total_bytes. The base it shares with other layers is reported beside it as shared_bytes and is not part of the total. The memory report breaks the layer's own part down with the option scope:

let r = g.memory_report(#{scope: "delta"});
[r.labels.map(|l| [l.label, l.elements]), r.shared_bytes, r.structure.removed_base_edges]

With #{scope: "delta"} the rows cover only the elements the layer added or modified (their labels and properties, as for a plain graph), the structure is the layer's own (its slots, indexes and totals, base_stubs, removed_base_vertices, removed_base_edges), and the base is the one figure shared_bytes. A removed base element is only counted, since the layer holds nothing of it but a tombstone. The indexes rows show the index bytes the layer owns: nothing for an index it shares with the base, the whole index for one it created. Without the option (#{scope: "all"}) the report walks every element the layer shows, base elements included, so it has the same rows as a report on the graph the layer shows. On a plain graph #{scope: "delta"} reports the whole graph, since a plain graph owns everything it shows.

On the generated large graph (222 210 elements) with 1 100 vertices modified and 500 added, the delta report read 1 600 elements and the full report 222 210 (debug build: 62 ms against 769 ms). The layer's own total was 475 KB beside a shared base of 51 MB.

Trying a layer from the command line

graphersal --layer runs the session on an empty layer over the --graph: the loaded graph becomes the frozen base, and every write goes to the layer.

graphersal --graph modern --layer \
  -e 'g.add_v("person").property("name", "ada").iterate()' \
  -e 'g.v().has("name", "marko").property("age", 30).iterate()' \
  -e 'g.v(6).drop().iterate()' \
  -e 'g.v().group_count().by(__.layer()).next()' \
  -e 'g.layer_diff(#{kinds: "vertex"})'

"added": 1
"base": 4
"modified": 1
"added": [#{"id": "7", "kind": "vertex", "labels": ["person"], "properties": #{"name": "ada"}}]
"modified": [#{"base_labels": ["person"], "id": "1", "kind": "vertex", "labels": ["person"], "properties": #{"age": #{"base": 29, "layer": 30}}}]
"removed": [#{"id": "6", "kind": "vertex", "labels": ["person"], "properties": #{"age": 35, "name": "peter"}}]
"truncated": false
  • The base can be any --graph source: a sample graph, a GraphSON or GraphML file, a packed snapshot (.gsnap), or a Store. A Store is opened read-only, without its lock, and nothing is written into it, so a layer can run over a store another process has open. --schema applies to the base as without --layer. The embedding models of a Store or .gsnap base serve the layer: embed(), text nearest and vector rules on the layer use them.
  • The REPL (graphersal --layer) and the dev server (graphersal --graph <src> --layer --server) run on the layer too. The server's start banner has a layer row; the playground pages and the server's MCP endpoint query the layer (MCP graph_info shows a layer block: the base's name and identity, what the layer added, modified and removed, its own and the shared bytes; the instructions of initialize name layer(), has_layer() and g.layer_diff(), on a layer only). "Save to file" is refused (409, "the graph is a layer kept in memory over its base"): it would write the layer's graph over the base's file.
  • The layer lives as long as the process: nothing is saved when it ends. To keep it, use a layer store (next section).
  • --layer is refused with --create-store (a layer never writes its base, so it cannot create a store; --layer-store <dir> --create-store keeps the layer in a new layer store) and with --read-only (the layer is the part that takes the writes), with exit code 2. A base the layer cannot carry yet (see below) is refused with exit code 2 too.

In the playground

The playground shows where each element of a layer comes from. Nothing of this appears for a plain graph.

  • The layer badge. The top bar shows "Layer over base" after the graph's counts, with the change counts +added ~modified −removed. Its tooltip names the base commit and splits the memory into the layer's own bytes and the shared base. A click opens the Layer changes dialog.
  • The drawing. In the Graph panel, an added vertex has a solid outline and a modified vertex a dashed outline. An added edge is solid and wider, a modified edge dashed. The colours are a colour-blind-safe pair (blue for added, reddish purple for modified), with light and dark variants. Base elements look exactly as on a plain graph. The legend adds the entries added, modified and base, and the inspector shows an origin row.
  • The Layer changes dialog lists what g.layer_diff() returns: Added, Modified and Removed, vertices before edges. A modified element shows each changed property as base → layer, a property only one side has as (absent) on the other, and a label change as the row labels. You can filter by kind and label and choose a limit. When more changes match than the limit shows, a "Truncated" notice says so. A click on an added or modified entry draws its neighbourhood in the Graph panel (for an edge, the neighbourhood of its out vertex) and opens the element in the inspector. Removed elements are listed only.
  • Memory. The process memory bar (Profile → Statistics, Optimize → Memory) gets a striped "Shared base" track below the layer's own segments. It is shared with every other layer over the base. In the tracked process heap it is part of other. Optimize → Memory has a Delta only switch: the memory report then walks only the layer's added and modified elements (scope: "delta"), and the base stays the single figure shared_bytes.
  • Discard all changes. The Layer changes dialog has Discard all changes… on every writable layer, in the browser and on the dev server (--layer, --layer-store). After a confirmation it discards everything the layer changed (see Discarding a layer's changes) in one commit; the layer stays and shows its base again, the badge counts drop to zero. It is not offered on a read-only server or while a read-only view of a past state is open.
  • Starting a layer in the browser. The WebAssembly playground can make a layer without a server. Load a graph, then choose Store ▸ Start a layer over this graph. Writes now go to the layer and the badge shows them. Drop layer in the Layer changes dialog discards the layer and brings the base back unchanged. The layer has no Store menu. Stop restarts the engine and restores the graph as it was loaded or last saved, so the layer is lost. On the dev server the layer comes from --layer / --layer-store, and neither action is offered.

The UI profile key layerDiff turns the badge, the dialog and its actions on or off (the built-in full profile has it on).

Discarding a layer's changes

A reset throws away everything a layer changed and keeps the layer: afterwards it reads exactly as its base, g.layer_diff() is empty and the badge shows +0 ~0 −0. The base is never written, so other layers over it are not affected. Use it to start a project layer over from scratch without building a new layer or a new layer store.

WhereHow
RustLayeredGraph::reset_layer(), or Graph<LayeredGraph>::reset_layer() (also on a layer store's live graph, store.graph().reset_layer())
Playgroundthe Layer changes dialog, Discard all changes…
Dev serverPOST /api/layer/reset (no body)
Session (embedding hosts)Session::reset_layer()

What it discards:

  • the vertices and edges the layer added (with the edges they had to base vertices);
  • its changes to base elements: properties and labels are the base's again;
  • the base elements it removed: they are back, with the ids, labels, properties and edges they have in the base;
  • its own schema and catalog changes (saved queries, jobs, property indexes defined or dropped on the layer): both are the base's again.

It is one commit, an ordinary unit like a query: it succeeds or leaves the layer as it was, a dry run or a failing transaction around it changes nothing, and commit hooks get its change set (the drops, the values written back and the base elements created again). On a layer store the commit is in the write-ahead log like any other, so a reopen or a recovery gives the reset layer, and store rollback can go back before it. The cost follows the size of the layer's changes, not of the base. A layer without changes commits nothing.

What it keeps: the commit position and history, the store and its settings, and the id sequences: an element created after the reset gets a new id, never one handed out before. Workload statistics are not graph data and stay as they are.

A related rule makes the reset replayable: a vertex created with the id and exactly the state of a base vertex the layer removed (the same labels in the same order, the same properties in the same order) is that base vertex again, not a new element; the same holds for an edge with the id, endpoints, label and properties of a removed base edge. Such an element counts as base and the diff no longer lists it.

use std::sync::Arc;
use graphersal::prelude::*;
use graphersal::storage::{Graph, LayerDiffRequest, LayeredGraph};

let base = Arc::new(TraversalGraph::tinkerpop_modern());
let layer = Graph::new(LayeredGraph::over(base).unwrap());
GraphTraversalSource::new(&mut *layer.write())
    .v("1").property("age", 30).iterate().unwrap();
GraphTraversalSource::new(&mut *layer.write()).add_v("person").iterate().unwrap();

let reset = layer.reset_layer().unwrap();
assert_eq!((reset.added.vertices, reset.modified.vertices), (1, 1));
assert!(layer.read().layer_diff(&LayerDiffRequest::new()).unwrap().is_empty());
assert_eq!(layer.read().vertex_count().unwrap(), 6);

Keeping a layer durably: --layer-store

graphersal --graph <base> --layer-store <dir> runs the session on the layer kept in the layer store <dir> over the base: every commit goes to the layer store's write-ahead log before the query answers, exactly as with a --graph <store>, and the base is never written. --create-store creates the layer store (with --on-damage, as for a plain store); later runs open it over the same base.

graphersal store create product --from modern          # the base: a Store
graphersal --graph product --layer-store project --create-store \
  -e 'g.add_v("person").property("name", "ada").iterate()'
graphersal --graph product --layer-store project \
  -e 'g.v().group_count().by(__.layer()).next()'

note: created the layer store project
  base: product
  base identity: graph 01a200ad-0cec-7d75-8f50-725adf107e99 at commit 0 (commit time 0)
  damage policy: maintenance
"added": 1
"base": 6
  • The base must keep its identity from one run to the next: a Store (opened read-only, without its lock, so another process may have it open) or a packed snapshot (.gsnap). A sample graph or a GraphSON/GraphML file gets a new identity at every load, so it is refused (exit 2) with the commands that make it a Store first (graphersal store create <base_dir> --from <graph>).
  • A layer store opens only over the base it was created over. Another base exits 1 with the message naming both (LayerBaseMismatch); so does a plain store given as --layer-store. --graph <layer store> alone is refused too: it names the base to give.
  • --layer-store implies --layer; both together are the same durable layer. --read-only loads the layer store read-only (no lock, nothing written, every write refused); with --create-store it is refused (exit 2). A backup of a layer store opens read-only over the base the same way.
  • The REPL and the dev server (--server) run on it. The server commits to the layer store, its start banner shows a Store section with the layer store's path, its base and its commit position, and Ctrl+C closes it cleanly. "Save to file" answers 409 ("every commit is already durable in it"); the server's Store panel serves plain stores only, so it is not offered for a layer store: use graphersal store ... on it.

Store commands on a layer store

The graphersal store commands that read or copy files work on a layer store without the base: info (its base is a row of the "fixed at creation" block), list, marks, journal, attic (the listing and changes), backup (it warns that the backup is useless without the base), restore, export (a layer snapshot), convert and upgrade. The commands that load the layer take --base <SOURCE>, the base it was created over (a store or a .gsnap):

CommandWith --base
store verify <dir> --base <src>also loads every snapshot over the base (without --base: every checksum, plus a note)
store checkpoint <dir> --base <src>encodes the layer over the base: a snapshot the size of its changes
store fork <dir> <new> [TARGET] --base <src>a new layer store over the same base
store rollback <dir> TARGET --base <src>rolls the layer back in place; the attic keeps the rest
store attic <dir> restore|remove|fork ... --base <src>as for a plain store
store materialize <dir> <file.gsnap> --base <src> [TARGET]the whole graph the layer shows, as a standalone packed snapshot

Without --base these commands are refused (exit 1) with the LayerStore reason and the command to run instead. store materialize writes the base's elements with the layer's changes applied, the layer's schema and catalog (format version 4, the base's embedding models it uses unless --without-models); the file needs no base, so any Graphersal reads it (--graph whole.gsnap, store create <dir> --from whole.gsnap):

graphersal store materialize project whole.gsnap --base product

Materialized the layer store project at commit 1 into whole.gsnap
  vertices: 7
  edges: 6
  standalone: yes: the whole graph (base and layer), it needs no base
  # open it in the REPL
  graphersal --graph whole.gsnap

store repair refuses a layer store (a repair salvages whole graphs: restore a backup of it), and so do store models remove|default (a layer store keeps no embedding model; store models <dir> says its graph serves the base's).

Rust

A layer is the storage LayeredGraph over an Arc<TraversalGraph>. Everything that runs on a Graph<S> runs on it: the typed traversal API, the DSL, GQL and the session.

use std::sync::Arc;
use graphersal::prelude::*;
use graphersal::storage::{ElementKind, Graph, LayerDiffRequest, LayerOrigin, LayeredGraph};

let base = Arc::new(TraversalGraph::tinkerpop_modern());
let layer = Arc::new(Graph::new(LayeredGraph::over(Arc::clone(&base)).unwrap()));

// The DSL on the layer: the writes go to the layer, the base stays as it was.
let run = |script: &str| graphersal::script::eval_value(layer.clone(), script).unwrap();
run(r#"g.add_v("person").property("name", "ada").iterate()"#);
run(r#"g.v().has("name", "marko").property("age", 30).iterate()"#);
assert_eq!(run(r#"g.v().has_layer("added", "modified").count().next()"#).as_int(), Ok(2));
assert_eq!(run(r#"g.v().has("name", "ada").layer().next()"#).to_string(), "added");

// The typed API: origins and the diff.
let read = layer.read();
let g = GraphTraversalSource::new(&*read);
let diff = g.layer_diff(&LayerDiffRequest::new().kind(ElementKind::Vertex)).unwrap();
assert_eq!((diff.added.len(), diff.modified.len(), diff.removed.len()), (1, 1, 0));
assert_eq!(diff.modified[0].properties[0].name, "age");
assert!(diff.to_json().starts_with(r#"{"added":"#));
let marko = read.get_vertex_by_id("1").unwrap().unwrap();
assert_eq!(read.vertex_layer(marko).unwrap(), Some(LayerOrigin::Modified));
assert_eq!(TraversalGraph::vertex_count(&base), 6);

A layer built with LayeredGraph::over gets the base graph alone. The embedding models of a database live beside the graph, in its Graph; LayerBase keeps them together with the frozen graph and a display name, and LayerBase::new_layer() makes a Graph<LayeredGraph> that serves them. A clone of a LayerBase is cheap: every layer made from it shares one base and one set of models.

use graphersal::prelude::*;
use graphersal::storage::LayerBase;

// A Store's graph (`Store::open_read_only(..)?.into_graph()`) or a `.gsnap` read
// (`graphersal::persist::read_snapshot_file`) brings its models along the same way.
let base = LayerBase::from_graph(Graph::new(TraversalGraph::tinkerpop_modern()))
    .unwrap()
    .with_name("product");
let project_a = base.new_layer().unwrap();
let project_b = base.new_layer().unwrap();
GraphTraversalSource::new(&mut *project_a.write()).add_v("repo").iterate().unwrap();
assert_eq!(project_a.read().vertex_count().unwrap(), 7);
assert_eq!(project_b.read().vertex_count().unwrap(), 6);

LayerBase::base_ref() names the base's identity: its graph lineage id, its last commit and that commit's time. A layer snapshot (graphersal::persist::write_snapshot of the layer, or write_graph_snapshot of its Graph) holds only what the layer added and changed plus that identity, so it is about the size of the project's changes, not of the product. It is read back over the same base with graphersal::persist::read_layer_snapshot(reader, &options, &base); over another base (another graph, or the same product graph after more commits) it is refused with a message naming both bases, and read_snapshot refuses it as a whole graph. A base saved as a .gsnap or Store and loaded again keeps its identity and takes its layers' snapshots.

LayerDiff::to_property() is the map of the table above with its keys in that order, and LayerDiff::to_json() its JSON text. A storage that has no layers answers LayerOrigin::Base and an empty diff from the trait's defaults.

Python

graph.layer_diff(kinds=None, labels=None, limit=None, policy=None) answers the diff as a dict with the keys in the order of the table above. layer() and has_layer() are DSL steps and run in graph.query(...) like every other step.

import graphersal

graph = graphersal.Graph.tinkerpop_modern()
assert graph.query("g.v().layer().dedup().to_list()") == ["base"]
assert graph.layer_diff(kinds="vertex", limit=10) == {
    "added": [], "removed": [], "modified": [], "truncated": False,
}

A Python Graph cannot be a layer yet: it always holds a graph of its own, so from Python every element is "base" and the diff is empty. The functions are there so that queries and code written for layers already run.

Limitations

  • Discarding only part of a layer. A reset discards everything; to keep some changes, roll a layer store back to a mark or a time instead (store rollback), or write the changes back by hand.
  • Persistence. From Rust a layer can be saved as a layer snapshot (above) or kept in a layer Store, which journals every commit and opens again only over the same base (graphersal store info shows a layer store's base); the CLI and the dev server keep it there with --layer-store (above). --layer and Python keep it in memory. A layer store is backed up, restored, verified and exported like any store; every copy holds the layer only, so a backup of a layer store is useless without its base (the backup's report and graphersal store backup say so): keep the base, or export a standalone copy of the whole graph the layer shows (Store::export_materialized, graphersal store materialize: a plain .gsnap that any Graphersal reads). Forks, rollback, the attic and conversion to another backend work on a layer store and keep it a layer over the same base. A damaged layer store is not repaired (restore a backup of it, or rebuild the layer), and the embedding models of a layer store are changed in its base.
  • One level. The base is a plain graph; there is no layer over a layer. The base is frozen for good: when the product graph changes, project layers are rebuilt over the new base.
  • Refused for now, with an error naming the feature ("... not supported on a layered graph yet"): compression rule and embedding model definitions created on a layer.
  • Vector rules: a layer over a base with vector rules keeps the derived vectors in step as a plain graph does. Creating the layer embeds nothing: the base's vectors are read as they are. A write on the layer to a rule's source embeds the element in the same unit, with the same vectors, errors and change sets as a plain graph with the layer's data; a write that leaves the text as it was copies nothing into the layer. A rule the layer adds or changes on a label the base holds fills every element of that label, so it copies each of them into the layer: the preview (validate_schema, diff_schema) names how many (base_copies, and a sentence in the warning text). A layer uses the embedding models of its base: over a Store or a .gsnap that holds models (--layer, or LayerBase in Rust), rules, embed() and text nearest on the layer run with them as on the base. A layer cannot import or define models of its own. A layer built over a bare graph without its models (LayeredGraph::over in Rust) serves only the built-in hash-ngram/1: a write that needs another model fails ("the model ... is not served here") and leaves nothing, as on a plain graph without that model.
  • Property indexes: a layer serves the base's indexes for its own data, also after it changed elements: lookups and counts answer from the index, as on a plain graph. The base's unique indexes hold for the layer: a write that would give a second element a unique value fails with the same error a plain graph with the layer's data gives, and a value that an element of the base held before the layer dropped or changed it is free again. A unique index the base keeps disabled (it was stored over repeated values) stays disabled on the layer. A layer can create, drop and redefine indexes (g.create_index(...), g.drop_index(...)) for itself: the base and the other layers keep theirs. A unique index is checked against the layer's data, as on a plain graph. Creating an index on a layer reads every element of its label in the base once and keeps its own copy of the index, which counts in the layer's g.memory_usage().
  • Order: unordered results list the same elements as a plain graph with the same data, in the same order, except after some removals (details on the developer page). Use order() when the order matters.
  • Not in GQL yet. GQL queries run on a layer like on any graph, but GQL has no function for an element's origin or the diff yet. Use the DSL for those.
  • The playground cannot draw removed elements. They are no longer in the graph, so the Layer changes dialog lists them as text only (see In the playground). The Fast drawing tier draws edge origins by colour and width only (WebGL has no dashed lines); the edge's hover label names its origin.
